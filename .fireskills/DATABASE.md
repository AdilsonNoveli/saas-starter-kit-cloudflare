## Decisions, Ownership, and Retention

Technical details: `fireskill-specialist-drizzle`.

### Sources and Conventions

- **Database change policy (absolute, owner decision 2026-09-30)**: isolation by history (layers toggled in `config.ts`), a specific step per capability, adjustments edit the init of the owning history and the database is reset and redeployed from zero (until the application launches; the reset is not part of `bun run deploy`), a new numbered init only on a version bump. Full text in `.fireskills/RULES.md`; never patch migrations, `ALTER` chains or expand/contract.

- **PostgreSQL** via Cloudflare Hyperdrive (`infra/database.ts`); Drizzle ORM (`drizzle-orm/postgres-js`). PostGIS enabled since initial migration. `apps/web` uses **D1** (`DB`) exclusively for `@nuxt/content`; it is not application data.
- SQL identifiers in PascalCase; `id` is `text` (cuid2; `User` uses `crypto.randomUUID()`); timestamps are `timestamptz` with `created_at`/`updated_at`. Column names mix `camelCase` and `snake_case`: do not normalize (causes destructive migrations).
- No session table exists: sessions and credentials live in the KV store `AuthKV`, written by the issuer (`apps/functions/src/auth.ts`). Since SPEC-0009 each session is a record under `["oauth:refresh", "user:<id>", <token>]` whose `properties` carry the session's `sid`, and `["email", <e-mail>, "subject"]` holds `user:<id>`; revocation reads only that person's prefix (`apps/functions/src/session-store.ts`). Records issued before that change are read by no flow and expire on their own; `bun run db:reset` also purges `oauth:refresh` (`scripts/reset-database-core.ts`). Behaviour of the session: `.fireskills/PROJECT.md`.
- `layers/account` (`layers.core`, SPEC-0009) owns no table and has no migration history yet: it reads and writes `User` and `MfaRecoveryCode` (base history) and deletes rows of `layers/teams` and `layers/notifications` through the `@nuxfire/functions/schema` barrel. SPEC-0009 added no table, column or migration. `packages/crypto` and `packages/rate-limit` hold no data: the rate-limit counters stay in each Worker's own KV (`hubKV()` in the app, `AuthKV` in the issuer).
- The barrel `apps/functions/src/database/schema.ts` re-exports each layer's schema unconditionally (typed client only — no query cost, since a disabled layer's router is never mounted). Migrations (SPEC-0006, 2026-09-28, extended same-day to admin/notifications/teams): **seven independent histories**, not one gated array — base (`apps/functions`, only `core-schema.ts` now: `User`, `MfaRecoveryCode`, `WaitlistEmail`, `Log`) plus one per layer that owns tables and has its own `drizzle.config.ts`: `layers/admin`, `layers/notifications`, `layers/teams`, `layers/account` (all `layers.core`, always applied; `account` got its first history with SPEC-0010), `layers/kanban`, `layers/billing` (both `layers.features`, gated). `teams` got its own history last: moving `Job`/`DeadLetterRecord` into `layers/teams/server/database/schema.ts` (their FKs to `Team` were the base's only physical dependency on teams) turned the previous bidirectional cycle with `core-schema.ts` into a one-directional one (`TeamInvite.invitedById` → `User`), the same shape every other split layer already had. Applied via `scripts/run-migrations.mjs` in `infra/utils/nuxt.ts` — every `layers.core` layer with its own history unconditionally, every `layers.features` layer with its own history gated on `config.ts`. A feature that is `false` never runs its migration at deploy time — its tables never exist in that database, not even empty. See `apps/functions/src/database/MIGRATIONS.md`.
- **Base migration history consolidated (2026-09-28, two rounds)**: `apps/functions/src/database/migrations/0000_init.sql` was regenerated from scratch twice the same day — first to drop the old `0000_init.sql`/`0001_pending_purchase.sql`/`0002_plan_public_offer.sql`/`0003_team_plan_nullable_and_billing_feature.sql` history in favor of a single clean file scoped to `layers.core`, then again after `admin`/`notifications`/`teams` each split out their own tables, leaving the base with only `User`, `MfaRecoveryCode`, `WaitlistEmail`, `Log` — every table now has exactly one `CREATE TABLE` source, no dual provenance. Safe only because this project is a SaaS kit forked fresh by third parties (the one environment developed against was reset, not bootstrapped, each time); see `apps/functions/src/database/MIGRATIONS.md`'s consolidation notes before repeating this against a fork with real data.

### Relations and Rules Not Expressed in Schema Columns

- Foreign keys, split by history (2026-09-28, three consolidation rounds): base `apps/functions/src/database/migrations/0000_init.sql` has 1 — `MfaRecoveryCode.userId` → `User` (`ON DELETE CASCADE`). Teams `layers/teams/migrations/0000_teams.sql` has 6 — `Job`, `DeadLetterRecord` → `Team`; `Permission` → `Role`; `TeamMembership.roleId` → `Role`; `TeamInvite` → `Team`, `Role`, and `User` (`invitedById`, the layer's only physical FK back into base). Admin `layers/admin/migrations/0000_admin.sql` adds `PlatformAdmin` → `User`. Account `layers/account/migrations/0000_account.sql` (SPEC-0010) adds `UserPreference`, `UserSession` and `EmailChangeRequest`, each `userId` → `User` with `ON DELETE CASCADE`. Notifications `layers/notifications/migrations/0000_notifications.sql` adds none (`Notification.userId` is relation-only, no physical FK). Billing `layers/billing/migrations/0000_billing.sql` adds `Plan.buyerTeamId` → `Team` (`ON DELETE SET NULL`), `Subscription` → `Team` and `Plan`, `PendingPurchase.planId` → `Plan`, `PendingPurchase.claimedByUserId` → `User`, `PendingPurchase.resultTeamId` → `Team` (`ON DELETE SET NULL`). Kanban `layers/kanban/migrations/0000_kanban.sql` adds `KanbanBoard` → `Team`, `KanbanColumn` → `KanbanBoard`, `KanbanCard` → `KanbanColumn`.
- Column only, without FK: `TeamMembership.teamId` and `userId`, `Role.teamId`, `BenefitsOnPlan.planId` and `benefitId`, `Log.jobId`, `AuditLog.actorUserId` (deliberate: log persists after user deletion), `Notification.userId` (Drizzle `relations()` only, to avoid circular import), and, since SPEC-0005, `Team.planId` (no relation on the `teams` side either — the query relation lives in billing's own schema.ts, since `teams` must never import a feature layer) and `Team.maxSeats` (denormalized by billing, `null` = unlimited).
- `PlatformAdmin.role` (enum `platform_role`: `SUPER_ADMIN`, `SUPPORT`) does not appear in detected list above: scanner ignores enum columns.
- Two deliberate schema cycles remain (core↔teams, core↔notifications), both relation-only now — no physical FK crosses either boundary in either direction except `TeamInvite.invitedById` → `User` (teams→base, one-directional). `core-schema.ts`'s `logRelations` imports `jobs` back from `layers/teams` (SPEC-0006, teams split, 2026-09-28) purely for a Drizzle relation (`Log.jobId` has no `.references()`), the same shape as its `usersRelations` → `notifications` import. Both work solely because all cross-file references reside inside callbacks. `teams↔billing` was a third cycle until SPEC-0005 made it one-directional (billing→teams only).
- `Role.teamId = null` = shared system role (Owner, Admin, Member). `Permission` has composite key `(action, roleId)`.
- `Team.status` is `text` (`ACTIVE` | `SUSPENDED`), not an enum. `Team.slug` has a unique index (`Team_slug_unique`) in the init of `layers/teams` since SPEC-0010: two concurrent creations with the same slug can no longer both pass the application check, and `createTeamWithOwner` turns the violation into `slug_taken`.
- `UserPreference` (SPEC-0010): one row per person, created only when the onboarding finishes, so its absence is what sends a person to `/onboarding`. `locale` (`en`, `pt-br`, `es`), `theme` (`system`, `light`, `dark`), `dateFormat` (`DMY`, `MDY`, `YMD`) and `nameOrder` (`WESTERN`, `EASTERN`) are text validated by `parsePreferences`, not enums, like every other status-like column here. The server is the source of the preference; the `i18n_redirected` and `nuxt-color-mode` cookies only mirror it for the first paint.
- `UserSession` (SPEC-0010): one row per login, keyed by the `sid` the token carries; it holds only metadata for the sessions list (browser and system from the `User-Agent`, country, region and city from `request.cf`, creation and last use). It never holds the IP, latitude, longitude or postal code. Whether a session is still alive is decided by the issuer's refresh records, not by this table. `expiresAt` slides thirty days on each token renewal, and the hourly `apps/functions/src/cron.ts` removes rows ninety days after `expiresAt`.
- `EmailChangeRequest` (SPEC-0010): at most one per person; stores only the HMAC of the two six-digit codes (one sent to the current address, one to the new one), the attempt count and a fifteen-minute expiry. Removed on confirmation, exhaustion or replacement.
- `MfaRecoveryCode`: single-use recovery codes, one set per `(userId, scope)` where `scope` is `user` (backs `User.mfaSecret`) or `platform` (backs `PlatformAdmin.mfaSecret`). Only an HMAC-SHA256 of the code is stored (keyed with the factor's own encryption key, bound to scope and user); `usedAt` is set atomically on redemption. Unique on `(userId, scope, codeHash)`; regenerating or disabling MFA deletes the whole set. Set/replace logic: `layers/account/server/utils/mfa-recovery.ts` (the pure generation, format and keyed hash are in `packages/crypto`); manual reset: `apps/functions/src/database/reset-mfa.ts`.
- `mfaSecret` (on `User` and `PlatformAdmin`) is always encrypted (AES-GCM) and never exposed in client sessions.
- Plans are database rows created in `/admin/plans`; only the **Free** plan and system roles are seeded (idempotent seed on each deploy).
- `Plan.buyerTeamMode` (`NEW_TEAM` default, or `EXISTING_TEAM`) and `Plan.buyerTeamId` record, per plan, where a buyer lands after paying: a team of their own (as Owner) or the existing team named by `buyerTeamId` (required, and only meaningful, for `EXISTING_TEAM`). Set in `/admin/plans`.
- `PendingPurchase` (SPEC-0004): a buyer with no team pays before creating an account; this row holds the checkout until an authenticated claim resolves `Plan.buyerTeamMode` into a real team/membership. `providerCheckoutId` is unique (Stripe Checkout Session id, or `paddle:<id>` for Paddle, which has no server-created session); `providerSubscriptionId`/`providerCustomerId` stay null until the provider confirms the subscription. `status` (`PENDING` | `CLAIMED` | `EXPIRED` | `REJECTED`) is text, like every other status-like column in this schema. `claimedByUserId` → `User`, `resultTeamId` → `Team` (`ON DELETE SET NULL`, like `Plan.buyerTeamId`). Expiry (30 days) is computed lazily on read (`getPendingPurchase`), not swept by a cron job. Indexed on `email` and `status`.

### Retention and Backup

- Retention: no retention policy declared in code. `Log` and `AuditLog` grow without automated purge; audit logging is append-only by convention. Retention decision pending.
- Backup: no scheduled database backup exists (verified absent).
