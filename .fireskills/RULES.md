# System Rules

These rules complement agent instructions without superseding specs or acceptance criteria. Evidence for each lives in the referenced specialist.

## Architecture

- Separation of Concerns: one file, single responsibility.
- Extreme componentization; folder and file structures designed for maintainability.
- DRY: maximum code reuse. YAGNI: do not implement unrequested functionality. KISS: simplest robust solution.
- Business domain lives in `layers/`; `apps/app` (Composition Root) contains no domain business logic. See `fireskill-specialist-nuxfire-layers`.
- "Active layer" has a single source of truth: `config.ts` → `activeLayerNames`. Never determine activation by disk presence.
- Abilities (`defineAbility`) carry layer prefix; tRPC procedures do not. Each layer router exports a `routers` map matching `satisfies`.
- Drizzle Schema: barrel `apps/functions/src/database/schema.ts` imports each layer by **package specifier**, never relative path.
- **ABSOLUTE AND UNBREAKABLE RULE — database change policy (owner decision, 2026-09-30)**. It overrides every older text in this repository, including expand/contract, "additive migration", bootstrap and rollback guidance:
  1. **Isolation by history.** The base history (`apps/functions`) holds only what makes login and the platform work. Every layer that owns tables has its own history (`layers/<name>/migrations/`) and is switched on or off in `config.ts`; a layer that is off never runs its history, so its tables never reach the database.
  2. **A new capability is a specific, well-defined, direct step.** A capability that needs tables gets its own layer and history (or extends the history of the layer that owns it), containing only what that capability needs. Never a catch-all, never tables or extensions for something not being implemented now (example: `pg_trgm` and `unaccent` belong to the people layer and `vector` to the AI layer, each created in that layer's init).
  3. **Adjustments edit the init and reset the database.** Any change to an existing table, column, index, constraint or extension is made by editing the `0000_*` init of the owning history: remove the old init, its `meta/*_snapshot.json` and its `_journal.json` entry, regenerate it from the schema with `drizzle-kit generate`, and re-add by hand any non-generated line such as `CREATE EXTENSION`. The database is then **reset and brought up again from zero** by the responsible person (the guarded `bun run db:reset`, then `bun run deploy`, which re-applies every history and the seed). This is ALWAYS the standard until the application launches: no patch migrations (`0001_fix…`), no `ALTER` chains, no expand/contract, no bootstrap scripts.
  4. **A new init number only on a version bump.** A history receives a new numbered init (`001_init.sql`, as the owner wrote it; drizzle-kit's native numbering has four digits, to be reconciled at the first bump) only when the application is raised to a new version such as V02. This whole policy is in force until the application launches; what applies after launch is not defined yet, and the owner must decide it before the first production data exists.
  5. **Who resets.** Agents edit the init and the code but **never run a destructive database command** (`DROP`, `TRUNCATE`, schema reset); the reset is carried out by the responsible person. The reset is **not** part of `bun run deploy`, which only applies migrations and the seed (audit of 2026-09-30: an edited init is not re-applied on a database that already recorded it). It is a separate, guarded command — `bun run db:reset -- --stage <stage>`, specified in SPEC-0007 — that removes the `public` and `drizzle` schemas and purges the `AuthKV` user keys; until it exists, the responsible person does the same by hand (`DROP SCHEMA public CASCADE`, `DROP SCHEMA drizzle CASCADE`, plus the `AuthKV` keys) and then runs `bun run deploy`.
  6. **Data that must survive.** A stage the owner declares as holding data that must survive is the only exception, and every destructive action on it needs explicit, per-action authorization.
- **ABSOLUTE RULE — migration history per layer (SPEC-0006, 2026-09-28)**: there is no single, shared migration history. Base (`apps/functions/drizzle.config.ts`, `layers.core` only) and every feature layer that owns tables (`layers/<name>/drizzle.config.ts`, `layers.features`) each have their own, completely independent `migrations/` folder and tracking table (`drizzle.__drizzle_migrations_<name>`). A new feature layer with persistent tables **always** gets its own `drizzle.config.ts`/`migrations/`, generated and applied from that layer's own directory — never added to the base's schema array, never generated from `apps/functions/`. `infra/utils/nuxt.ts`'s deploy loop already discovers any `layers.features` entry with a `migrations/` folder automatically — a correctly-added feature layer requires **zero** changes to that file. Migrations are applied only via `scripts/run-migrations.mjs`, never `drizzle-kit migrate`'s own CLI (crashes without a TTY — see `fireskill-specialist-sst`). Full recipe, checklist, and the two documented exceptions to "never hand-edit an applied migration": `fireskill-specialist-drizzle/references/new-table-recipe.md`.

## Code and Quality

- Strict typing, **zero `any`**, enforced by `scripts/no-explicit-any.test.ts` (parses every tracked `.ts`/`.vue`). Third-party constraints that require `any` are derived from the library (see `AnyAbility` in `apps/app/server/trpc/trpc.ts`), never restated.
- Zero dead or speculative code; clean, verified, optimized implementation.
- **One place per fact (owner decision, 2026-09-30)**: product direction, closed decisions and the order of the phases live only in `_roadmaps/plano-mestre-serelius.md` (each decision is recorded as an ADR in `docs/adr/`); what exists in the code lives only in `.fireskills/PROJECT.md` and in each spec's verified research; the decisions of a phase interview live only in its backlog; requirements, scenarios and proof live only in the spec. Every other file points to these, it does not copy them. There is no `MVP.md`: phases come from the plano, and the backlog and the spec of a phase are created from it when that phase starts (never in advance). The mirrors demanded by the database change policy are the one deliberate exception, guarded by `scripts/db-policy.test.ts`.
- **Scaffolding follows the phase that uses it (ADR-0010, 2026-09-30)**: no folder, package, layer, app, table, extension, column or infrastructure resource is created before the phase whose deliverable uses it. The target structure in `_roadmaps/plano-mestre-serelius.md` (Part 1.2) is a destination, not a task list. Every phase interview checks each listed item against "which M01 deliverable uses this?" before accepting it.
- **Reference verbs need proof (owner decision, 2026-09-30)**: "copy" or "migrate" from a reference app (`_reference-*`) is valid only after the spec's research proves, with file evidence, that the repository has no equivalent. If it does, the verb is "extend" or "move" and the existing code is the base: nothing already working is rewritten or duplicated.
- Styling and customization rules (semantic tokens only, `packages/tokens` as the single source): `.fireskills/DESIGNSYSTEM.MD`. See `fireskill-specialist-nuxt-ui`.
- Inside Workers, never log raw `Error` objects: serialize `message`, `name`, `stack`.

- **References are read-only (SPEC-0007)**: `_reference-app`, `_reference-person` and `_reference-web` stay on disk for consultation, out of version control (`.gitignore`) and out of every scan; the originals are never edited. Anything migrated is **copied** and its header carries the origin, in the first 20 lines: `@copied-from <path inside the reference>`, `@commit <sha of the reference>` and `@license <SPDX id or file>`. `scripts/references-policy.test.ts` fails a copied file that lacks the commit or the license.

## Testing

- Vitest is the test runner (`bun run test`). Each layer with tests has its own `vitest.config.ts` (`apps/app` and the `billing`, `kanban` and `teams` layers also have a `vitest.setup.ts` that exposes `defineAbility` as a global, because Nuxt's auto-import does not exist in Vitest). `scripts/`, `packages/tokens`, `packages/crypto` and `packages/rate-limit` are their own projects, each listed by name in `vitest.config.mts`.
- `nuxt typecheck` does **not** cover server routes: also run `bunx vue-tsc --noEmit -p server/tsconfig.json` in `apps/app`.
- Green `tsc`/`vitest`/`nuxt build` does **not** prove deployment: for `apps/functions` and `layers/`, the real verification gate is `sst deploy` on a test stage.
- Tests never run against development database (`fireskills/skills/fireskill-setup/scripts/check_database_safety.mjs`).

## Security and Privacy

- Secrets in `SCREAMING_SNAKE_CASE`, identical across `.env.example`, `infra/secret.ts`, and `Resource.<NAME>`; only public values carry `NUXT_PUBLIC_`. Never commit or expose `.env.stage` / `.env.production`.
- Installation identity (product name, domain, full sender e-mail) is only the `BRAND_*` variables of the stage env file, read solely by `scripts/branding.ts`; never hardcode a domain, sender or brand name in code, and never add defaults for them.
- Empty secret routes **fail closed** (platform and user MFA).
- Internal Worker `Auth` endpoints require constant-time `x-admin-secret`.
- `platformAdminProcedure` requires active `PlatformAdmin` + MFA + elevated 30-minute session; never derived from `abilityProcedure`.
- Seeds that run on deploy (`apps/functions/src/database/seed/index.ts`) never create admins or carry credentials. `apps/functions/src/database/seed/demo-accounts.ts` and `apps/functions/src/database/grant-platform-admin.ts` and `apps/functions/src/database/reset-mfa.ts` are manual-only; the demo script's default passwords are throwaway.
- Data reset of `User` requires purging both `AuthKV` keys (`["email", email, "password"]` and `["users", email]`).

- **One source per security primitive (SPEC-0009)**: AES-GCM secret encryption, HMAC-SHA256, the constant-time secret comparison (`secretsMatch`), the pure half of the MFA recovery codes and the WebSocket ticket exist only in `packages/crypto` (`@nuxfire/crypto`); the fixed-window rate-limit algorithm exists only in `packages/rate-limit` (`@nuxfire/rate-limit`). Every consumer imports them explicitly, never through Nitro auto-import; a Worker or route keeps only a thin wrapper (KV binding, client IP, h3 error). Both packages stay pure: Web Crypto and Cloudflare types only, no h3, Nitro, database or layer import, no runtime dependency beyond each other. `scripts/primitives-policy.test.ts` fails a copy outside the two packages and an impure import.

## Operations

- Deployment: `bun run deploy -- --stage <stage>` (`--stage` CLI flag is mandatory; never `SST_STAGE=`). Production has `retain` + `protect`.
- Migrations: apply **only** via deployment, following the database change policy above (edit the init of the owning history and reset the database; no patch migrations, no rollbacks, no expand/contract).
- Do not modify without verified understanding: `linker = "hoisted"`, split `unenv` (root v2 / apps v1), exact version patches, `ssr: false` on auth views.
- Optional Cloudflare resources live behind `flags` in `config.ts`; code gracefully handles missing bindings.
- See `fireskill-specialist-sst` and `fireskill-specialist-cloudflare-workers`.

## Specific Project Rules

- **Dark mode mandatory across all UI surfaces.**
- **User notifications via `useNotification`** (`success`/`error`/`info`/`warning`/`message`/`confirm`); `useToast()` is called only inside the three `useNotification` wrappers (`apps/app`, `apps/login`, `apps/web`) and `window.confirm` is never used, enforced by `scripts/notification-rules.test.ts`. Error messages from `catch` come from `getErrorMessage(error)` (`apps/app/shared/utils/error-message.ts`).
- **Media and file storage via Cloudflare R2** (`hubBlob()` in NuxtHub, S3-compatible API); there is no AWS S3 bucket in this project.
- Always apply clean-up improvements to files within touched scope.
- **Blog posts and content pages (SEO contract).** Every post under `apps/web/content/blog` declares `title`, `description`, `date`, `author` and `lang` (`en`, `pt-br` or `es`; there is no default and it is never inferred), a raster `ogImage` (`.png`/`.jpg`, generated from the SVG cover with `bun run generate:og`), and the same `translations` block on every language version (each language to its slug, itself included). **Every post exists in all three languages** (`en`, `pt-br`, `es`), each with its own cover when the image has text: the site follows the visitor's language, and `check:seo` rejects a post that lacks one. Titles are specific and never carry the brand (it is appended); every page has one `<h1>` and its own description. Metadata comes only from the builders in `apps/web/app/utils/seo/content-seo.ts` through `useArticleSeo`/`usePageSeo`: a layout that renders content never leaves the SEO module’s fallback title. A content URL that resolves to nothing answers 404, never 200. Build with the real `SITE_URL` and run `bun run check:seo` before declaring content work done. Writing posts: load `fireskill-specialist-content-seo`.
- **Human-readable text (copy contract).** Every string a person reads in `apps/*`, `layers/*` and `packages/emails` (interface text, errors, empty states, emails, notifications, docs, landing, pricing, legal; not the names of menus, tools and features) is written with `fireskill-specialist-copywriting`, lives in the locale files (`en`, `pt-br` and `es` change together, `bun run check:i18n`) and never as a literal in a `.vue` template. A number, comparison, guarantee, result, price, deadline, named source or testimonial needs a record in `.fireskills/CLAIMS.yml` with a verifier a machine can run; a countdown or "only today" exists only with a real, dated limit in the ledger; a testimonial is a person who exists, used the product and consented, shown with their own photo or with none. `bun run check:copy` enforces it; known defects are dated entries of `scripts/copy-baseline.json`, each owned by a spec or backlog item, and the list only shrinks. Not legal advice: the owner confirms the rules of the markets served.
- **Public page weight and delivery.** Changes to what `apps/web` ships to the browser (scripts, images, fonts, third-party code, hydration, `routeRules`) load `fireskill-specialist-web-performance`; the budgets and their dated baselines are in `perf-budgets.json` and only shrink; `bun run check:perf` runs against a fresh build. LCP, INP and CLS are recorded by the lab protocol of the specialist and never claimed from the byte gate.
- **What search engines require of a page.** Status codes, redirects, canonical, sitemap and `lastmod`, robots directives, structured data and IndexNow are governed by `fireskill-specialist-seo`: a moved URL is a `301` line in `apps/web/public/_redirects` (never a `redirect` route rule or a meta refresh), the `Web` Worker serves `drop-trailing-slash`, the sitemap `lastmod` carries date and time, no `FAQPage`, no rating or review markup without real reviews. `bun run check:seo` (and `--live` against a running server) enforces it. `bun run indexnow` is a dry run unless the owner authorizes `--submit`.
