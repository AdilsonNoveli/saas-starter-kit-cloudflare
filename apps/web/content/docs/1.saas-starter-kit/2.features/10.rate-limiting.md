title: "Rate Limiting"
description: "Fixed-window rate limiting backed by Cloudflare KV, protecting login, MFA, and payment webhook endpoints."
---

A fixed-window rate limiter backed by Cloudflare KV, implemented in `@nuxfire/rate-limit` (`packages/rate-limit`) with adapters for both Worker runtimes:

- `packages/rate-limit/core.ts` — pure fixed-window algorithm (`rateLimit(store, key, { limit, windowSeconds })`), zero runtime dependencies.
- `packages/rate-limit/adapters.ts` — storage adapters: `hubKvStore()` for NuxtHub's `hubKV()` inside `apps/app`, and `kvNamespaceStore()` for raw Cloudflare `KVNamespace` (`AuthKV`) in `apps/functions`.
- `apps/app/server/utils/rate-limit.ts` — provides `rateLimit` and `assertNotRateLimited(event, routeKey, options)` wrapping the pure engine for the App Worker.

```typescript [packages/rate-limit/core.ts]
export async function rateLimit(
  store: RateLimitStore,
  key: string,
  { limit, windowSeconds }: RateLimitRule,
  now: () => number = Date.now,
): Promise<RateLimitResult> {
  const window = Math.max(windowSeconds, MIN_WINDOW_SECONDS);
  const storeKey = `ratelimit:${key}:${Math.floor(now() / 1000 / window)}`;
  const count = ((await store.get(storeKey)) ?? 0) + 1;
  await store.set(storeKey, count, window);
  return { allowed: count <= limit, count, limit };
}
```

`assertNotRateLimited(event, routeKey, options)` wraps this for HTTP routes on the App Worker: it keys by `<routeKey>:<ip>` and throws `429 Too Many Requests` directly when the limit is exceeded.

## What's currently protected

| Where | Keyed by | Purpose |
|---|---|---|
| `apps/functions/src/auth.ts` (`enforceCredentialRateLimit`) | path + IP + email | Password/code login on the auth Worker |
| `layers/admin/server/api/admin/mfa/verify.post.ts` | platform admin id | MFA enrollment attempts |
| `layers/admin/server/api/admin/mfa/challenge.post.ts` | platform admin id | MFA reauthentication attempts |
| `layers/billing/server/api/webhooks/stripe.post.ts` | IP | Stripe webhook, on top of signature validation |
| `layers/billing/server/api/webhooks/paddle.post.ts` | IP | Paddle webhook, on top of signature validation |

This isn't a general-purpose API throttle — it's applied specifically where credential/signature validation alone doesn't stop a high-volume replay: authentication attempts and unauthenticated webhook endpoints. There's no rate limiting on ordinary tRPC procedures today.
