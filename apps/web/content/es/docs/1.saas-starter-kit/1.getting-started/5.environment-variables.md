Cada una de las variables a continuación reside en `.env.example` (la plantilla) y se carga en la bóveda de secrets de SST por cada etapa: consulte [Secrets](/docs/saas-starter-kit/getting-started/secrets) para ver los comandos de carga. Esta página sirve como referencia de **dónde proviene cada valor**, plataforma por plataforma, para cualquiera que realice esta configuración por primera vez.

No necesita rellenar todas las filas: complete solo lo que requiera una función que realmente vaya a utilizar. Todo lo que no esté marcado como **Siempre** está condicionado por un flag en `config.ts`; déjelo en blanco y desactive el flag si no desea esa integración.

## 1. Branding — your identity

Se definen en la sección **Branding** del archivo de env de su etapa: el único lugar donde viven su dominio y su correo de envío; nada en el código los repite. A diferencia de todo lo que sigue, estas **no son secrets**: el despliegue las lee directamente del archivo (y se detiene indicando el nombre de la variable si falta alguna o está mal formada), y una variable de entorno real con el mismo nombre tiene precedencia. Cada etapa lee su propio archivo: `.env.production` para `production`, `.env.stage` para todas las demás etapas.

| Variable | Required | What it is |
|---|---|---|
| `BRAND_NAME` | Always | El nombre de su producto o empresa: nombre del remitente, asunto y texto alternativo del logotipo en los correos. Hasta 80 caracteres. |
| `BRAND_DOMAIN` | Always | Su dominio de producción, solo el nombre (`acme.io`), sin `https://`, ruta ni puerto. Debe ser una zona activa en la misma cuenta de Cloudflare propietaria de su token de API. `production` responde en él; todas las demás etapas responden en `<stage>.dev.<dominio>`. |
| `BRAND_EMAIL` | Always | La dirección **completa** del remitente (`contact@acme.io`), solo la dirección: el nombre visible proviene de `BRAND_NAME`. Su dominio debe estar verificado en su proveedor de correo; puede ser un subdominio como `mail.acme.io`. |

## 2. Cloudflare — deploy authentication

Requerido antes de que cualquier comando `sst` funcione, en cada máquina que realice despliegues. La guía completa con capturas de pantalla (permisos, alcance del token) se encuentra en [Acceso a Cloudflare](/docs/saas-starter-kit/getting-started/cloudflare-access).

| Variable | Required | Get it at |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | Always | [dash.cloudflare.com](https://dash.cloudflare.com) → **Manage Account → Account API Tokens** → **Create Token**. No es la página personal `profile/api-tokens`: esa lista otro tipo de token. |
| `CLOUDFLARE_ACCOUNT_ID` | Always | [dash.cloudflare.com](https://dash.cloudflare.com) → el menú **⋮** junto al nombre de su cuenta → **Copy Account ID** (también aparece en la sección API de la página Overview de cualquier dominio) |

## 3. Database — PostgreSQL

Cualquier Postgres estándar funciona: la aplicación se comunica mediante el protocolo de cable nativo, nunca mediante un SDK de proveedor. Utilizando [Supabase](https://supabase.com) como ejemplo (a donde apunta el `.env.stage` de este proyecto):

| Variable | Required | Get it at |
|---|---|---|
| `DATABASE_HOST` | Always | [supabase.com/dashboard](https://supabase.com/dashboard/project/_/settings/database) → su proyecto → **Settings → Database** → pestaña **Direct connection**. Vea la advertencia a continuación: no use la pestaña del pooler. |
| `DATABASE_PORT` | Always | Misma pestaña (`5432`) |
| `DATABASE_NAME` | Always | Misma pestaña |
| `DATABASE_USER` | Always | Misma pestaña: solo `postgres`, sin sufijo |
| `DATABASE_PASSWORD` | Always | Misma pestaña: definida cuando se creó el proyecto; restablézcala allí si no la tiene |

### Use the Direct connection, not the Session pooler

La página de configuración de la base de datos de Supabase muestra dos modos de conexión. **Utilice la conexión Direct** — la [documentación oficial de Hyperdrive de Cloudflare es explícita al respecto](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/): *"debe utilizar la cadena de conexión Direct connection en lugar de las cadenas agrupadas (pooled), ya que Hyperdrive se encargará de agrupar las conexiones para garantizar un acceso óptimo desde los Workers."* Hyperdrive ya agrupa conexiones en el borde de Cloudflare; enrutarlo a través del propio pooler de Supabase (Supavisor) implicaría agrupar dos veces sin ningún beneficio.

**Los dos modos utilizan formatos de host y nombre de usuario diferentes y no intercambiables; nunca mezcle el host de un modo con el usuario de otro:**

| | Host | User |
|---|---|---|
| **Direct** (utilice este) | `db.<project-ref>.supabase.co` | `postgres` |
| Session pooler (no lo use para `DATABASE_HOST`/`DATABASE_USER`) | `aws-0-<region>.pooler.supabase.com` | `postgres.<project-ref>` |

Vincular un host de modo directo con un nombre de usuario de modo pooler (o viceversa) no falla con un error descriptivo inmediato: se despliega y luego Cloudflare lo rechaza con `Hyperdrive → 400: "Invalid database credentials"` (código de error 2013), lo que parece un error de contraseña incluso cuando la contraseña es correcta.

**El único caso en el que podría necesitar el pooler:** cada despliegue ejecuta las migraciones de base de datos automáticamente desde **su propia máquina** (`infra/utils/nuxt.ts`, un comando local), utilizando estos mismos valores, y no desde el borde de Cloudflare. La conexión directa de Supabase es exclusivamente IPv6. Si su red carece de una ruta IPv6 real a Internet, ese paso de migración local no podrá conectarse (un tiempo de espera de conexión, no el error de credenciales anterior), a pesar de que Hyperdrive funcionaría bien desde la red IPv6 de Cloudflare. Si se encuentra con este fallo específico, cambiar al par del Session pooler (tabla anterior) es la solución pragmática: intercambia un leve overhead de doble pooling por la accesibilidad desde su propia máquina.

Si utiliza RDS, Neon o Postgres autohospedado: los mismos cinco valores se obtienen de la página de información de conexión de ese proveedor; a la aplicación no le importa cuál sea, siempre que la extensión `postgis` esté habilitada (Supabase la tiene disponible por defecto; ejecute `CREATE EXTENSION IF NOT EXISTS postgis;` en los demás si es necesario).

## 4. Email — pick at least one provider

Habilite/deshabilite cada uno en `config.ts` → `flags`. Solo `resend` viene activado por defecto.

| Variable | Provider | Required when | Get it at |
|---|---|---|---|
| `RESEND_API_KEY` | Resend | `flags.resend` | [resend.com/api-keys](https://resend.com/api-keys) → **Create API Key** |
| `MAILGUN_API_KEY` | Mailgun | `flags.mailgun` | [app.mailgun.com](https://app.mailgun.com/) → **Settings → API Keys** |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Amazon SES | `flags.ses` | [console.aws.amazon.com/iam](https://console.aws.amazon.com/iam/home#/security_credentials) → cree un usuario IAM con permisos de envío SES → **Security credentials → Create access key**. Aún no automatizado en infraestructura (vea el comentario en `infra/secret.ts`): el usuario IAM debe crearse manualmente. |
| `SPARKPOST_API_KEY` | SparkPost | `flags.sparkPost` | [app.sparkpost.com](https://app.sparkpost.com/) → **Account → API Keys** |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` | Generic SMTP | `flags.smtp` | Panel de su propio proveedor de SMTP: no hay un enlace único aquí ya que acepta cualquier servidor SMTP |

## 5. Social login

Ambos son opcionales y se activan independientemente (`flags.githubAuth`, `flags.googleAuth`). Cada URL de retorno a continuación debe coincidir **exactamente**, incluido el sufijo `/callback`; de lo contrario, el proveedor de OAuth rechazará el inicio de sesión con un error de URI de redirección no coincidente.

| Variable | Required when | Get it at |
|---|---|---|
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | `flags.githubAuth` | [github.com/settings/developers](https://github.com/settings/developers) → **New OAuth App**. Authorization callback URL: `https://auth.<your-domain>/github/callback` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | `flags.googleAuth` | [console.cloud.google.com/apis/credentials](https://console.cloud.google.com/apis/credentials) → **Create Credentials → OAuth client ID** (tipo: Web application). Authorized redirect URI: `https://auth.<your-domain>/google/callback` |

## 6. Payments

Stripe y Paddle pueden estar activos simultáneamente: una fila de `Plan` solo selecciona un proveedor por registro (consulte [Pagos y Facturación](/docs/saas-starter-kit/features/payments)).

| Variable | Required when | Get it at |
|---|---|---|
| `STRIPE_SECRET_KEY` | `flags.stripe` | [dashboard.stripe.com/apikeys](https://dashboard.stripe.com/apikeys) |
| `STRIPE_WEBHOOK_SECRET_KEY` | `flags.stripe` | [dashboard.stripe.com/webhooks](https://dashboard.stripe.com/webhooks) → **Add endpoint** → `https://app.<your-domain>/api/webhooks/stripe` → copie el **Signing secret** que se muestra |
| `PADDLE_API_KEY` | `flags.paddle` | [vendors.paddle.com/authentication](https://vendors.paddle.com/authentication) → **Developer Tools → Authentication → pestaña API keys** (pruebas en sandbox: [sandbox-vendors.paddle.com](https://sandbox-vendors.paddle.com/authentication)) |
| `PADDLE_WEBHOOK_SECRET` | `flags.paddle` | [vendors.paddle.com/notifications](https://vendors.paddle.com/notifications) → **New destination** → Webhook → `https://app.<your-domain>/api/webhooks/paddle` → copie la clave secreta mostrada |
| `PADDLE_CLIENT_TOKEN` | `flags.paddle` | Misma página de **Authentication** que `PADDLE_API_KEY` — pestaña **Client-side tokens**. Esta es pública por diseño (termina en el bundle del navegador), pero sigue configurándose por etapa al igual que las demás. |

### PADDLE_API_KEY permissions — don't select "All"

Al crear la clave de API, la aplicación solo accede a dos recursos de Paddle en el lado del servidor (`grep -rn "paddle\.\w*\.\w*(" apps/app/server` para verificar):

- **Customers** — **Read**. `paddle.customers.get(customerId)` en el controlador del webhook (`server/api/webhooks/paddle.post.ts`), para leer el correo electrónico del cliente.
- **Customer portal sessions** — **Write**. `paddle.customerPortalSessions.create(...)` (`server/trpc/routers/billing.ts`), para generar el enlace del portal de facturación que el cliente utiliza para gestionar su suscripción.

Nada más: no se utiliza ningún permiso de Adjustments, Businesses, Addresses, Discounts, Products, Prices, Transactions o Reports en ninguna parte del código base. Una clave con más permisos representa una superficie de riesgo innecesaria en caso de filtración; amplíe el alcance más adelante solo si el nuevo código realmente llama a otro recurso de Paddle. (`paddle.webhooks.unmarshal(...)`, la tercera llamada al SDK de Paddle en el mismo controlador de webhook, verifica la firma del webhook localmente: no es una llamada de red y no necesita permisos de API).

## 7. Platform Admin console (/admin)

No provienen de ninguna plataforma externa: genere estas variables usted mismo, de manera local. Consulte [Consola de Platform Admin](/docs/saas-starter-kit/features/platform-admin) para ver qué protegen.

| Variable | Required | How to generate |
|---|---|---|
| `PLATFORM_MFA_SESSION_SECRET` | Always, before `/admin/*` works | `openssl rand -base64 32` (Git Bash/macOS/Linux) — o en PowerShell: `[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`. Seguro de rotar: en el peor de los casos, cierra las sesiones elevadas activas. |
| `PLATFORM_ADMIN_ENCRYPTION_KEY` | Always, before `/admin/*` works | Mismo comando. **No rotar a la ligera**: cifra el secreto TOTP de cada administrador en reposo; rotarlo obliga a todos los administradores registrados a configurar MFA de nuevo. Guárdelo en un lugar seguro (un gestor de contraseñas), no solo en este archivo. |

## 8. Two-factor authentication (regular users)

El mismo comando de generación que el par de platform admin anterior, las mismas reglas, pero guardados en secrets independientes; consulte [Consola de Platform Admin](/docs/saas-starter-kit/features/platform-admin) para conocer el motivo. Solo se requiere si un usuario activa realmente 2FA desde Configuración de Cuenta → Seguridad; nada más en la aplicación depende de estas variables.

| Variable | Required | How to generate |
|---|---|---|
| `USER_MFA_SESSION_SECRET` | Before any user can enable 2FA | `openssl rand -base64 32`. Seguro de rotar: en el peor de los casos, solicita nuevamente un código a los usuarios ya inscritos en su próxima solicitud. |
| `USER_MFA_ENCRYPTION_KEY` | Before any user can enable 2FA | Mismo comando. **No rotar a la ligera**: cifra el secreto TOTP de cada usuario en reposo; rotarlo obliga a todos los que lo activaron a configurar 2FA de nuevo. |

## 10. Optional — build tuning

| Variable | Required | Notes |
|---|---|---|
| `SST_BUILD_CONCURRENCY_SITE` | No | Limita la cantidad de paquetes que SST compila en paralelo. Útil en ejecutores de CI con CPU limitada; déjelo sin configurar en caso contrario. |

## What never goes in this file

Las variables `NUXT_PUBLIC_*`, URLs de workers, IDs de cliente expuestos al navegador y cualquier otro valor derivado en el despliegue se computan automáticamente mediante `infra/*.ts`; nunca los defina a mano aquí. La única excepción: la ejecución manual de `seed/demo-accounts.ts` necesita `AUTH_URL` y `AUTH_ADMIN_SECRET` en el entorno de su terminal al momento de ejecutarlo (no en este archivo ni en la bóveda); consulte [Consola de Platform Admin](/docs/saas-starter-kit/features/platform-admin).
