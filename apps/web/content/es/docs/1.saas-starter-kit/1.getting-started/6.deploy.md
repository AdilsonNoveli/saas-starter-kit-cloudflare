## Your first deploy

```bash
bun run deploy
```

Despliega en su etapa de desarrollo personal (SST utiliza el nombre de usuario de su sistema como nombre de la etapa de forma predeterminada).

Antes de tocar Cloudflare, `bun run deploy` ejecuta una verificación previa (`scripts/doctor.ts`, también disponible por separado como `bun run doctor`). Detiene el despliegue, con la corrección exacta, cuando algo que se sabe que lo rompe está mal:

- faltan los enlaces de los workspaces `@nuxfire/*` (no se ejecutó `bun install` en esta carpeta);
- `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` no están definidos en su shell, o el token es inválido, expiró o pertenece a otra cuenta;
- el archivo de secrets de la etapa (`.env.stage`, o `.env.production` para producción) tiene valores `DATABASE_*` vacíos;
- el Branding de ese mismo archivo (`BRAND_NAME`, `BRAND_DOMAIN`, `BRAND_EMAIL`) falta o está mal formado: la misma validación que ejecuta el propio despliegue.

Lo que no puede comprobar (por ejemplo, que su dominio no aparezca en la cuenta) se muestra como aviso (`!`) y no detiene el despliegue. Para comprobar el archivo de secrets de producción, ejecute `bun run doctor -- --stage production`.

**Prompt para agentes de IA:**
```text
Run bun run deploy. It runs a preflight check first — if that reports a
problem, fix what it says before retrying. If the deploy itself fails,
check the error against AGENTS.md's
Infra / SST gotchas and Database sections before proposing a fix —
several documented failures (Supabase pooler/direct mismatch, missing
workers.dev subdomain, unenv version conflicts) read like a different
problem than they actually are.
```

## What happens automatically

`apps/functions/src/database/seed/index.ts` se ejecuta en cada despliegue, inmediatamente después de las migraciones, y crea el plan Free más los roles/permisos del sistema; es idempotente, por lo que ejecutarlo nuevamente nunca duplica nada. Los planes de pago se excluyen deliberadamente (los IDs de precios de Stripe/Paddle son por entorno); el propietario de la plataforma los crea en `/admin/plans`.

La cuenta del propietario de la plataforma y la consola `/admin` protegida por MFA son un paso manual y deliberado; consulte [Consola de Platform Admin](/docs/saas-starter-kit/features/platform-admin).

## Deploying to other stages

- **Desarrollo**: utiliza el nombre de usuario de su sistema como nombre de etapa por defecto; esto es lo que hace `bun run deploy` sin flags adicionales.
- **Producción**: complete `.env.production` con valores reales de producción (incluida su propia sección Branding), cárguelo y despliegue:
  ```bash
  bunx sst secret load .env.production --stage production
  bun run deploy -- --stage production
  ```
- **Etapas personalizadas**: `bun run deploy -- --stage custom-name` (el `--` es necesario para pasar el flag a través del envoltorio `bun run`).

**Prompt para agentes de IA:**
```text
For production: confirm .env.production is filled with real production
values (never copy .env.stage's values into it), then run
bunx sst secret load .env.production --stage production (no --fallback)
followed by bun run deploy -- --stage production. If the user needs a
platform-owner account, that's a separate step — see the Platform Admin
Console doc, and never seed a known owner password on a real environment.
```
