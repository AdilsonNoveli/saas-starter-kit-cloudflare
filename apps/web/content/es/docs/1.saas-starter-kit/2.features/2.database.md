Nuxfire utiliza **Postgres** como su base de datos principal, alcanzada desde Cloudflare Workers a través de [Hyperdrive](https://developers.cloudflare.com/hyperdrive/), con [Drizzle ORM](https://orm.drizzle.team/).

## Database Architecture

### 1. Schema Definition

Las definiciones de tablas se distribuyen entre `apps/functions/src/database/core-schema.ts` y el `server/database/schema.ts` de cada capa, utilizando el dialecto Postgres de Drizzle (`pgTable`, `pgEnum`). `apps/functions/src/database/schema.ts` es un agregador que reexporta todas ellas (`export * from "./core-schema"` más una línea por layer) bajo la ruta de importación `@nuxfire/functions/schema`:

- **`core-schema.ts`** — Usuarios, Registros (Logs), Correos de Waitlist.
- **`layers/teams/server/database/schema.ts`** — Equipos, Membresías de Equipo, Invitaciones de Equipo, Roles, Permisos, Trabajos (Jobs), Registros de Dead Letter.
- **`layers/billing/server/database/schema.ts`** — Planes, Beneficios, Beneficios por Plan, Suscripciones.
- **`layers/notifications/server/database/schema.ts`** — Notificaciones.
- **`layers/admin/server/database/schema.ts`** — Administradores de Plataforma, Registros de Auditoría.
- **`layers/account/server/database/schema.ts`** — Preferencias de Usuario, Sesiones de Usuario, Solicitudes de Cambio de Correo.
- **`layers/kanban/server/database/schema.ts`** — Tableros Kanban, Columnas, Tarjetas.

Desactivar un layer de funcionalidad en `config.ts` (`layers.features`) elimina sus páginas y componentes del bundle de Nuxt y evita la ejecución de sus migraciones en el despliegue. Las capas principales (`teams`, `notifications`, `admin`, `account`) están siempre activas. Cada capa con tablas persistentes gestiona su propio historial independiente de migraciones (`drizzle.config.ts`, `migrations/`), separado del historial base en `apps/functions/src/database/migrations/`. Las referencias entre capas siempre usan especificadores de paquete (como `@nuxfire/layer-teams/...`), nunca rutas relativas fuera de la raíz del paquete.

### 2. Infrastructure Setup

Los Workers no pueden mantener una conexión TCP directa con Postgres, por lo que se accede a la base de datos a través de Hyperdrive, configurado en `infra/database.ts`:

```typescript [infra/database.ts]
export const database = new sst.cloudflare.Hyperdrive("AppDB", {
  origin: {
    scheme: "postgres",
    host: secret.DatabaseHost.value,
    port: secret.DatabasePort.value.apply(Number),
    database: secret.DatabaseName.value,
    user: secret.DatabaseUser.value,
    password: secret.DatabasePassword.value,
  },
});
```

Hyperdrive gestiona el pool y la caché de la conexión; la app siempre habla el protocolo de conexión nativo de Postgres, de modo que el origen es intercambiable (Supabase, RDS, Neon, autohospedado) sin tocar el código de la aplicación.

> **Modo de conexión de Supabase:** La documentación oficial de Hyperdrive en Cloudflare [recomienda explícitamente utilizar la conexión Direct de Supabase](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/) en lugar de cadenas agrupadas (pooler), ya que Hyperdrive realiza el agrupamiento de conexiones en el borde de Cloudflare (evitando doble pooling). Consulte [Variables de Entorno — Utilice la conexión Direct](/docs/saas-starter-kit/getting-started/environment-variables#use-the-direct-connection-not-the-session-pooler) para notas sobre formato de host/usuario y migraciones locales en IPv6.

### 3. Database Connection

`useDB()` (`apps/app/server/utils/db.ts`) construye un cliente `drizzle-orm/postgres-js` a partir del enlace de Hyperdrive, asignado a la petición actual y nunca almacenado globalmente en caché:

```typescript [apps/app/server/utils/db.ts]
function createDB() {
  const sql = postgres(binding.connectionString, { max: 5, fetch_types: false });
  return drizzle(sql, { schema });
}

export function useDB() {
  const event = useEvent();
  const ctx = event.context as { _db?: DB };
  if (!ctx._db) ctx._db = createDB();
  return ctx._db;
}
```

Esto es crítico porque un cliente `postgres.js` es un objeto de E/S, y Workers destruye la E/S de una petición una vez que esta concluye; reutilizar un cliente creado en una petición dentro de otra posterior causa fallos intermitentes (Cloudflare documenta esto como "Cannot perform I/O on behalf of a different request"). El pool de conexiones de Hyperdrive ya elimina el costo de abrir un cliente por petición, por lo que almacenar en caché entre peticiones no ofrece beneficios y sí riesgos.

## Database Usage

Ejemplo de consulta utilizando la API relacional de Drizzle:

```typescript
const team = await useDB().query.teams.findFirst({
  where: or(eq(teams.id, teamIdentifier), eq(teams.slug, teamIdentifier)),
  with: {
    memberships: {
      with: {
        user: { columns: { id: true, name: true, email: true, image: true } },
        role: { columns: { id: true, name: true } },
      },
    },
  },
});
```

## Database Migrations

Las migraciones se generan con Drizzle Kit a partir de `core-schema.ts` y el `server/database/schema.ts` de cada capa (la lista exacta declarada en `apps/functions/drizzle.config.ts` bajo `schema: [...]`, con `dialect: "postgresql"`) y se guardan en `apps/functions/src/database/migrations/`:

```bash
cd apps/functions
DATABASE_HOST=... DATABASE_PORT=5432 DATABASE_USER=... DATABASE_PASSWORD=... DATABASE_NAME=... \
  bunx drizzle-kit generate
```

Revise el SQL generado antes de confirmarlo en Git: Drizzle Kit compara los esquemas anteriores con la última instantánea en `migrations/meta/`, pero no puede conocer la intención (como renombrar una columna frente a eliminarla y recrearla), por lo que debe verificar minuciosamente cualquier cambio destructivo.

### Deployment

Cada despliegue del Worker `App` ejecuta `drizzle-kit migrate` automáticamente, justo después de compilar el Worker (consulte `infra/utils/nuxt.ts`), empleando los secrets `DatabaseHost`/`DatabasePort`/`DatabaseUser`/`DatabasePassword`/`DatabaseName`. No hay un paso de migración independiente para ejecutar a mano.

### Rollback strategy

Drizzle Kit no genera migraciones reversibles (down-migrations): las migraciones de Postgres son solo hacia adelante (append-only). En resumen (detalles en `apps/functions/src/database/MIGRATIONS.md`):

- **Cambios aditivos** (nueva tabla, columna opcional, índice) se pueden conservar de forma segura aunque se revierta el código del despliegue.
- **Cambios destructivos** (eliminar columna/tabla, nuevo `NOT NULL`, cambio de tipos) se envían en su propia migración, desplegada solo después de que el código que dependía del esquema antiguo haya estado en producción por un tiempo (el patrón estándar de expandir/contraer).
- Una migración errónea que llega a producción se corrige con una nueva migración hacia adelante, no con un rollback.
- Tome una copia de seguridad manual antes de cualquier migración que elimine o modifique columnas que contengan datos.
