## What's Included

- Notificaciones en tiempo real entregadas a través de WebSockets
- Preferencia de activación por usuario, guardada en `localStorage`
- Seguimiento del conteo de no leídas
- Interfaz de slideover para la lista de notificaciones

## Architecture

### Backend

La API de notificaciones es el enrutador tRPC en `layers/notifications/server/trpc/notifications.ts`:

- `list`: notificaciones del usuario actual, de más recientes a más antiguas.
- `create`: inserta una notificación y la publica inmediatamente mediante WebSockets en la misma llamada.
- `updateReadStatus`: marca un grupo de IDs de notificación como leídos.

```typescript [layers/notifications/server/trpc/notifications.ts]
create: protectedProcedure
  .input(z.object({ title: z.string(), message: z.string() }))
  .mutation(async ({ ctx: { user, sendWebsocketsEvent }, input }) => {
    const [notification] = await useDB().insert(notifications).values({ ...input, userId: user.id }).returning();
    await sendWebsocketsEvent(user.id, { type: "notification", payload: notification });
    return notification;
  }),
```

Consulte [WebSockets](/docs/saas-starter-kit/features/websockets) para conocer cómo `sendWebsocketsEvent` llega al navegador.

### Frontend state

`useNotificationsStore` (`layers/notifications/app/composables/use-notifications-store.ts`) es una store de Pinia:

- Mantiene las notificaciones indexadas por ID, además de un contador de no leídas.
- `initializeNotificationSettings()` / `setNotificationsEnabled()` guardan la preferencia de activación en `localStorage`.
- `fetchAllNotifications()`, `markAsRead()`, `createNotification()` envuelven las llamadas de tRPC anteriores.

### Real-time updates

`layers/notifications/app/plugins/ws-notifications.client.ts` se suscribe al tema del usuario actual a través del plugin de WebSocket; los eventos entrantes se incorporan a la store y los toasts los muestran cuando la preferencia está habilitada.

## Components

- `NotificationsSlideover.vue`: la interfaz de lista de notificaciones montada en el icono de campana del encabezado del panel de equipo.

## Sending to another user: the admin demo

`notifications.create` anterior solo notifica al *usuario emisor*; no existe un parámetro `targetUserId` porque nada determina aún quién tiene permiso para notificar a quién (eso requiere un rol cross-tenant real, que este starter kit no modela). Lo que sí incluye como demostración del pipeline en tiempo real dirigido a otro usuario es `/admin/notifications` (consulte [Consola de Platform Admin](/docs/saas-starter-kit/features/platform-admin)), una página para administradores de plataforma que elige un equipo, selecciona un miembro y le envía una notificación en tiempo real mediante un procedimiento dedicado:

```typescript [layers/notifications/server/trpc/admin-notifications.ts]
send: platformAdminProcedure
  .input(z.object({ targetUserId: z.string(), title: z.string(), message: z.string() }))
  .mutation(async ({ ctx: { sendWebsocketsEvent }, input }) => {
    const [notification] = await useDB().insert(notifications)
      .values({ title: input.title, message: input.message, userId: input.targetUserId })
      .returning();
    await sendWebsocketsEvent(input.targetUserId, { type: "notification", payload: notification });
    return notification;
  }),
```

Misma tabla y misma invocación de `sendWebsocketsEvent` que el enrutador de inquilinos; la única diferencia es que `userId` proviene de la entrada en lugar de la sesión del emisor, y el procedimiento está resguardado por `platformAdminProcedure` en lugar de `protectedProcedure`. Una función donde el propietario de un equipo notifique a sus miembros reutilizaría exactamente esta estructura una vez que la app cuente con un rol autorizado para invocarla.

## Settings

La preferencia se expone en dos ubicaciones, leyendo y escribiendo el mismo estado de la store:

- `layers/notifications/app/pages/account-settings/notifications.vue`: a nivel de cuenta.
- `layers/notifications/app/pages/[[team]]/settings/notifications.vue`: a nivel de equipo.
