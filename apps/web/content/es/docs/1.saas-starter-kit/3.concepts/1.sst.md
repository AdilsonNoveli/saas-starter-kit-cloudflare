[SST](https://sst.dev) es la capa de infraestructura como código sobre la cual se construye Nuxfire. Cada recurso de Cloudflare (Workers, Hyperdrive, KV, R2, D1, Queues, Durable Objects, Cron, DNS) es un recurso `sst.cloudflare.*` (o `sst.*` estándar) declarado en TypeScript bajo `infra/`, sin archivos `wrangler.toml`/`wrangler.json` manuales ni despliegues ejecutados fuera de SST.

## How the pieces load

El punto de entrada es `sst.config.ts`. Su método `run()` no lista recursos directamente: lee cada archivo `.ts` en `infra/` y lo importa, fusionando la exportación `outputs` de cada uno en las salidas finales de la infraestructura:

```typescript [sst.config.ts]
async run() {
  const outputs = {};
  for (const value of readdirSync("./infra/").filter((x) => x.endsWith(".ts"))) {
    const result = await import("./infra/" + value);
    if (result.outputs) Object.assign(outputs, result.outputs);
  }
  return outputs;
},
```

De esta forma, `infra/database.ts`, `infra/auth.ts`, `infra/app.ts`, `infra/jobs.ts`, `infra/websockets.ts`, `infra/cron.ts`, `infra/web.ts`, `infra/emails.ts`, `infra/dns.ts` e `infra/secret.ts` son módulos que declaran sus propios recursos, sin necesidad de mantener un archivo monolítico central.

La directiva `home: "cloudflare"` en la misma configuración indica que el estado de SST (recursos desplegados, IDs) se almacena en su cuenta de Cloudflare y no en AWS; no se requiere ninguna cuenta de AWS en esta configuración.

## Stages

Una **etapa** (stage) es un entorno aislado e identificado con un nombre propio: sus propios Workers, su propia conexión a la base de datos y sus propios secrets. `infra/dns.ts` se encarga de convertir el nombre de la etapa en un dominio:

```typescript [infra/dns.ts]
export const domain =
  { production: prodDomain }[$app.stage] || `${$app.stage}.${devDomain}`;
```

La etapa `production` se asigna a `prodDomain` de `config.ts`; cualquier otro nombre de etapa se asigna a `<stage>.<devDomain>`, por lo que `bun run deploy` sin flags ejecutado por un desarrollador llamado `alex` desplegará en `alex.dev.tudominio.com`.

`sst.config.ts` también otorga un tratamiento especial a `production` deliberadamente:

```typescript [sst.config.ts]
removal: input?.stage === "production" ? "retain" : "remove",
protect: ["production"].includes(input?.stage),
```

Los recursos de cualquier otra etapa se eliminan con `sst remove`; los de `production` se retienen y protegen contra eliminaciones accidentales.

## Secrets

Cada `sst.Secret` declarado por Nuxfire reside en `infra/secret.ts`, delimitado **por etapa**: cargar un valor en su etapa local nunca altera la bóveda de `production`, y viceversa. Consulte [Secrets](/docs/saas-starter-kit/getting-started/secrets) para ver el flujo exacto de `sst secret load`, y recuerde la excepción: `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` nunca son `sst.Secret`s; SST los requiere como variables de entorno reales en la terminal antes de poder autenticarse y leer la bóveda.

## Deploying

```bash
bun run deploy                          # your personal dev stage
bun run deploy -- --stage production    # production
bun run deploy -- --stage custom-name   # any other named stage
```

`bun run deploy` es un envoltorio fino de `sst deploy` (`package.json`); el separador `--` es necesario para que el flag `--stage` llegue a SST y no sea consumido por `bun run`.
