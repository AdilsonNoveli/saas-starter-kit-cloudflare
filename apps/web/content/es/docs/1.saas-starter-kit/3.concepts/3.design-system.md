title: "Sistema de Diseño y Marca"
description: "Cómo @nuxfire/tokens centraliza la tematización en las tres aplicaciones frontend y cómo personalizar la marca del starter kit para su propio producto."
---

Cada token de diseño (colores de marca, radio de esquinas, mapeo de superficies para modo oscuro y anulaciones de componentes de Nuxt UI) reside en un único paquete del workspace: `@nuxfire/tokens`, consumido por `apps/app`, `apps/web` y `apps/login` por igual. Antes de este paquete, cada aplicación duplicaba sus propios archivos `app.config.ts` y `main.css`, con el riesgo de que una de ellas divergiera silenciosamente. Personalizar la marca ahora requiere editar un solo archivo, no tres.

## The package

```
packages/tokens/
├── theme.css   # Tailwind @theme tokens, dark-mode mapping, corner radius
└── index.ts    # sharedUiConfig (Nuxt UI app.config.ts fragment) + enterpriseTableUi
```

Una aplicación consumidora lo enlaza en tres puntos:

```json [package.json]
{ "dependencies": { "@nuxfire/tokens": "workspace:*" } }
```

```css [app/assets/css/main.css]
@import "tailwindcss";
@import "@nuxt/ui";
@import "@nuxfire/tokens/theme.css"; /* after @nuxt/ui, so it wins over its defaults */
```

```ts [app/app.config.ts]
import { sharedUiConfig } from "@nuxfire/tokens";

export default defineAppConfig({
  ui: { ...sharedUiConfig }, // app-specific keys can follow the spread
});
```

### The @source gotcha

El paquete llega a cada aplicación mediante un enlace simbólico en `node_modules` (un workspace de Bun), y Tailwind no inspecciona `node_modules` en busca de nombres de clases por defecto. Sin la siguiente línea, cualquier clase que exista **únicamente** dentro de `index.ts` (por ejemplo, una variante en `compoundVariants` como `before:bg-primary/15`) se renderiza en el DOM sin ninguna regla CSS asociada (rota en silencio, sin emitir error). `theme.css` ya incluye la corrección:

```css
@source "./index.ts";
```

Si `index.ts` incorpora en el futuro una clase utilitaria genuinamente nueva (no utilizada previamente en el código fuente de la app), esta directiva es la que impide que quede inactiva.

## Brand accent — shared across all three apps

`flame` (rojo, `primary`) y `fire` (naranja, `secondary`) se definen una sola vez en `theme.css`, idénticos byte a byte en cada aplicación. `ui.colors` asigna `primary: 'flame'`, `secondary: 'fire'` en `sharedUiConfig`.

## Neutral scale — intentionally different per app

A diferencia del acento de la marca, la escala de superficie neutra (`night-*`) **no** se comparte; cada app define la suya en su propio `main.css`, usando los mismos nombres de tokens con matices diferentes:

- **`apps/app`** utiliza una escala de grises fríos, coincidente con paneles corporativos de referencia (estilo Linear); este es el panel de control activo y la consola de platform admin, donde una base neutra y el acento de marca reservado para acciones/destacados es el estándar de software SaaS (GitHub, Linear, Vercel adoptan la misma convención).
- **`apps/web`** y **`apps/login`** emplean un gris cálido con tintes ámbar, acorde a la identidad del sitio web público.

Cambiar el tono base de una app nunca altera las otras dos; modifique únicamente el bloque `--color-night-*` de dicha aplicación.

## Corner radius — one token drives everything

```css
:root {
  --ui-radius: 0.1875rem; /* 3px */
}
```

Nuxt UI deriva toda su escala `rounded-*` proporcionalmente a partir de esta única variable (`--radius-lg: calc(var(--ui-radius) * 2)`, etc.), de modo que cada tarjeta, botón, campo de entrada, modal e insignia se ajusta conjuntamente en una sola edición, sin necesidad de ajustes componente por componente.

## Shadow policy

Las superficies estáticas (tarjetas, secciones, paneles) utilizan **cero sombras**: la delimitación visual proviene de un borde/`ring` de 1px, nunca de `box-shadow`. Las capas superpuestas flotantes (modales, menús desplegables, popovers, tooltips) conservan su sombra: flotan sobre el contenido sin fondo oscurecido, por lo que la sombra es la única referencia de profundidad; este es el comportamiento predeterminado de Nuxt UI y se mantiene intacto.

## Component overrides (sharedUiConfig)

| Component | Override | Why |
|---|---|---|
| `UCard` | `bg-elevated` en lugar de `bg-default` | La variante estándar dejaba la tarjeta con el mismo tono que el fondo de la página (contraste 1:1, medido); `bg-elevated` proporciona un tono elevado. |
| `UAvatar` (neutro, sin imagen) | `bg-accented` en lugar de `bg-elevated` | El valor alternativo compartía el fondo de la propia tarjeta, por lo que un avatar sin foto carecía de fondo visible. |
| `UNavigationMenu` (vertical) | Iconos de 24px (antes 20px), filas colapsadas en cuadro centrado `size-11`, elemento activo recibe un `ring` de color además del tinte | Brinda un área de pulsación cuadrada clara y un estado activo con borde definido. |
| `UTabs` | Variante `link` por defecto en lugar de `pill` | Un bloque de color sólido de la marca resulta visualmente pesado comparado con el subrayado usado en pantallas de configuración. |
| `UTable` (`enterpriseTableUi`) | Encabezado pequeño, atenuado, en mayúsculas y espaciado | Coincide con la convención de columnas de tablas utilizada por Linear/Stripe/Notion, en vez de un encabezado grande. |

`enterpriseTableUi` se distribuye de forma independiente a `sharedUiConfig`, pasando explícitamente mediante la prop `:ui` de cada `<UTable>`; una prop de instancia siempre tiene prioridad.

## Accessibility — measured, not estimated

El mapeo de superficies claras y oscuras en `theme.css` proviene de mediciones reales de contraste sobre la aplicación en ejecución (fórmula de luminancia relativa de WCAG), no de estimaciones. El mapeo original de Nuxt UI midió una tarjeta en **1.00:1** frente al fondo (invisible) e iconos inactivos en **2.61:1** (por debajo del piso AA de WCAG de 4.5:1). La escala actual de texto en modo oscuro frente al lienzo `#0d0d0d`: 18.7:1 / 15.6:1 / 12.1:1 / 5.48:1; cada nivel supera el estándar AA, con el nivel `dimmed` intencionalmente más ajustado ya que también se usa en marcadores de posición (placeholders).

## Rebranding checklist

- **Cambiar el color de acento en todo el proyecto**: edite las escalas `flame-*`/`fire-*` en `packages/tokens/theme.css`.
- **Cambiar el radio de esquinas en todo el proyecto**: edite `--ui-radius` en el mismo archivo.
- **Cambiar la apariencia por defecto de un componente**: edite `sharedUiConfig`/`enterpriseTableUi` en `packages/tokens/index.ts`.
- **Cambiar el tono neutro de una sola app**: edite la escala `--color-night-*` en el `main.css` de esa aplicación (no en `packages/tokens`).
- **Anular estilos para una app en particular**: extienda `sharedUiConfig` en el `app.config.ts` de la app y añada propiedades después de extenderlo; la última definición prevalece.

Cada token es una propiedad personalizada de CSS, nunca una clase fijada en el componente, sirviendo de base para un futuro editor de temas por inquilino: sobrescribir variables `--ui-*`/`--color-*` en ejecución se propaga a todos los componentes de inmediato.
