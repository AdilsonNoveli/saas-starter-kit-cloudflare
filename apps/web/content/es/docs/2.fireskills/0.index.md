**Fireskills** es el método orientado a especificaciones que viene dentro de Nuxfire. Describes lo que quieres en el chat del agente de tu IDE; el agente sigue un flujo fijo (capturar, refinar, especificar, probar, implementar, documentar) y trabaja con un conjunto de especialistas técnicos que ya conocen este código.

En lugar de prompts sueltos, todo cambio pasa por un único archivo normativo, gates de calidad y evidencia. Cuando el código y la documentación no coinciden, **gana el código**.

**¿Eres nuevo aquí? Empieza por el [Inicio rápido](/docs/fireskills/getting-started/quick-start):** lista qué escribir en tu IDE para cada cosa que puedas querer hacer.

## Pilares

### 1. Una especificación normativa por porción

Toda funcionalidad, corrección o cambio vive en exactamente un archivo: `specs/<state>/<NNNN>-<slug>/spec.md`. Requisitos, escenarios Gherkin, tareas, checklists, evidencia de pruebas y gates están todos en él. No existen `plan.md`, `tasks.md` ni `research.md`.

### 2. Tres actos, tres gates

- El **Acto I, Definir** (Inbox, Backlog, Specify, Validate) termina en el **Definition Gate**.
- El **Acto II, Diseñar y Probar** (Tasks, TDD/BDD) termina en el **Plan Gate**: las tareas existen y las pruebas fallan por el motivo correcto (RED).
- El **Acto III, Entregar** (Implement, Documentator) termina en el **Delivery Gate**: pruebas en verde, tipos verificados, evidencia registrada, documentos de contexto al día.

### 3. 34 especialistas técnicos

Los carga el agente antes de tocar código en su área:

- **11 especialistas de la stack de Nuxfire**: Nuxt 4, `@nuxt/ui` v4, layers de Nuxfire, tRPC v10, Drizzle, `nuxt-authorization`, OpenAuth.js, Pinia, Billing (Stripe y Paddle), Cloudflare Workers, SST 4. Cada uno tiene un `references/nuxfire-*.md` con lo que existe en el código y lo que **no** existe.
- **23 especialistas de ingeniería**: TypeScript, PostgreSQL, Tailwind, arquitectura, diseño de APIs, seguridad, rendimiento, observabilidad, depuración, code review, accesibilidad, UX/UI, versionado, git y más.

### 4. Una CLI pequeña para las partes mecánicas

`bun run fireskill` (código en `fireskills/cli/`, Bun y TypeScript) mueve specs entre estados, define la nota de esfuerzo, valida una spec con un linter rápido, muestra el progreso, sincroniza milestones y gestiona lecciones aprendidas. Consulta la [referencia de la CLI](/docs/fireskills/cli/commands).

### 5. Contexto persistente en `.fireskills/`

`PROJECT.md`, `STACK.md`, `RULES.md`, `DATABASE.md`, `INTERFACE.md`, `DESIGNSYSTEM.MD`, `PACKAGES.md`, `USER-PROFILE.md` y `LESSONS.md`/`lessons.json`. Los agentes los leen antes de preguntarte nada. Consulta [Contexto del proyecto](/docs/fireskills/getting-started/project-context).

### 6. Seguridad en torno a la base de datos y a las acciones irreversibles

El código de servidor se ejecuta en Cloudflare Workers mediante SST. El flujo nunca hace deploy, borra datos ni ejecuta un comando destructivo en la base por su cuenta; un script de protección clasifica los comandos (`drizzle-kit push --force`, `db:wipe`, `DROP`, `TRUNCATE` y otros se rechazan incluso con tu aprobación), y las pruebas que llegan a PostgreSQL exigen una base de datos de prueba separada.
