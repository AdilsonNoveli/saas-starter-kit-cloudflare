**Skill:** `fireskill-04-validate` · **Hace preguntas:** solo si debe volver al backlog · **Modifica:** la cabecera y la sección 13 del `spec.md`; mueve la spec a `specs/defined/`

## Cuándo usarlo

La spec está escrita y quieres saber si está lista para planificarse. El flujo llega a este paso por sí solo después del Paso 3.

## Qué escribir

```text
Use $fireskill-04-validate para auditar specs/<estado>/<NNNN>-<slug>/spec.md, seu research/ e os gates antes das tarefas. Orquestre transições automáticas com anúncio, execução e retomada na mesma conversa.
```

Sustituye la ruta, por ejemplo `specs/draft/0001-convite-de-membros-por-e-mail/spec.md`.

## Qué hace el agente

1. Confirma el formato (`Formato: Specsfy/2.0`), los tres actos en orden, el slug igual al directorio, y que el paquete contiene solo `spec.md` y un `research/` opcional.
2. Ejecuta el validador estructural de la skill:

   ```bash
   node fireskills/skills/fireskill-04-validate/scripts/validate_spec.mjs specs/draft/<NNNN>-<slug>/spec.md --allow-draft
   ```

3. Hace una **revisión semántica**: compara research, requisitos, BDD, plan técnico, modelo de datos, contratos, TDD, matriz y tareas. Confirma al menos tres `AC` distintos para la funcionalidad y para cada `US`, `FR` y `NFR`. Para una pantalla exige que la sección 10 esté completa; un CRUD sin pantallas ni formularios es un `BLOCKER`.
4. Si la definición cambia la stack o la persistencia, exige que la Definition of Done cite `.specsfy/STACK.md` o `.specsfy/DATABASE.md`.
5. Devuelve exactamente un resultado:

   | Resultado | Significado | Qué ocurre |
   |---|---|---|
   | `READY` | ningún fallo estructural y ningún `BLOCKER` sin resolver | `Definition Gate: Passed`, `Status: Defined`, luego `bun run fireskill transition <id> defined`, luego pasa el turno a `$fireskill-05-tasks` |
   | `NOT READY` | un fallo estructural o un `BLOCKER` | `Definition Gate: Failed`, `Status: Draft`; vuelve a `$fireskill-02-backlog` si falta una decisión, o a `$fireskill-03-specify`/`$fireskill-update-spec` si la corrección ya está decidida |

La misma skill también cierra la entrega al final del flujo: en `specs/review/`, con el Delivery Gate pasado, mueve la spec a `completed`. Consulta el [Paso 7](/docs/fireskills/getting-started/step-implement).

## Dos validadores, dos trabajos

| Comando | Qué es | Qué verifica |
|---|---|---|
| `validate_spec.mjs` (la skill) | **El gate.** Lo usa `$fireskill-04-validate`. | Formato, actos y secciones, IDs, cobertura de al menos tres `AC` por requisito, contrato de interfaz, índice de research |
| `bun run fireskill validate <id> [--strict]` (la CLI) | **Un linter rápido** que puedes ejecutar tú mismo. | `Effort` entre 1 y 10, `Effort rationale`, `Status`; cinco secciones encontradas por título (contexto/problema, actores/requisitos/alcance, escenarios BDD, tareas, pruebas/evidencia); un escenario BDD; una lista de tareas. Los placeholders como `[TODO]` son avisos; `--strict` convierte los avisos en errores. |

El linter de la CLI **no** cuenta `AC`, no verifica el contrato de interfaz, no cambia los gates y no mueve la spec. Pasarlo no equivale al Definition Gate.

```bash
bun run fireskill validate 0001 --strict
```

```text
Status: VÁLIDO (Aprovado no linter de specs)
Erros: 0 | Avisos: 0
```

## `transition` no verifica los gates

`bun run fireskill transition <id> <folder>` mueve la spec un paso (`draft` ↔ `defined` ↔ `planned` ↔ `in-progress` ↔ `review` ↔ `completed`) y actualiza `Status`. **No** lee los gates: un salto como `defined` → `in-progress` se rechaza (`transição inválida`), pero nada te impide mover una spec cuyo gate está `Pending`. Deja que las skills hagan los movimientos; solo los hacen después de que su gate haya pasado.

## Opcional: ataca la spec primero

Para una spec de alto esfuerzo o arriesgada (Effort 7 o más), pide una revisión adversarial antes de aprobar. Consulta `$fireskill-the-fool` en [Otros puntos de entrada](/docs/fireskills/getting-started/other-entry-points).
