**Skill:** `fireskill-05-tasks` · **Hace preguntas:** no (vuelve al backlog si falta una decisión) · **Modifica:** las secciones 14 y 15 del `spec.md`; mueve la spec a `specs/planned/`

## Cuándo usarlo

La spec tiene `Definition Gate: Passed` y está en `specs/defined/`. El flujo llega aquí por sí solo después del Paso 4.

## Qué escribir

```text
Use $fireskill-05-tasks para preencher tarefas rastreáveis com checklist PREP/EXECUTE/VERIFY/VISUAL/EVIDENCE/IMPROVE em specs/<estado>/<NNNN>-<slug>/spec.md. Orquestre transições automáticas com anúncio, execução e retomada na mesma conversa.
```

## Qué hace el agente

1. Exige `Formato: Specsfy/2.0`, `Definition Gate: Passed` y `Status: Defined`. Ejecuta el monitor de contexto e inspecciona la stack, los comandos y las rutas reales (`layers/*`, `apps/*`) antes de escribir nada.
2. Reemplaza **solo** las secciones `14. Tarefas` y `15. Ordem de execução` del mismo `spec.md`. Nunca crea un `tasks.md`.
3. Escribe cada tarea con este formato:

   ```markdown
   - [ ] T001 [TEST] [TDD] [US-001] Derivar teste Vitest do BDD da spec em layers/teams/shared/utils/abilities.test.ts — Refs: FR-002, AC-003 — Depends: none
   - [ ] T002 [CODE] [US-001] Implementar validação em layers/teams/server/trpc/teams.ts — Refs: FR-002, AC-003 — Depends: T001
   ```

   Etiquetas permitidas después del ID: `[P]` (puede ejecutarse en paralelo), `[TEST]`, `[TDD]`, `[CODE]`, `[DOC]`, `[OPS]`, `[US-NNN]`, y `[MIGRATION]` junto con `[CODE]` u `[OPS]`.
4. Da a toda tarea el mismo checklist, en este orden:

   ```markdown
     - [ ] **PREP**: Confirmar escopo, IDs, dependências e baseline.
     - [ ] **EXECUTE**: Produzir a entrega no caminho declarado.
     - [ ] **VERIFY**: Executar a verificação focal adequada.
     - [ ] **VISUAL**: Conferir bordas, espaçamentos, margens, padding e tipografia do sistema; se não houver interface, registrar `Não aplicável` e o motivo.
     - [ ] **EVIDENCE**: Registrar comando, resultado e IDs nas seções 11–13.
     - [ ] **IMPROVE**: Registrar melhoria aplicada ou ausência justificada.
   ```

5. Aplica las reglas que vienen de la spec:
   - una tarea `[TEST] [TDD]` por `AC`, y toda tarea `[CODE]` depende de su predecesor TDD con un RED válido;
   - una tarea `[CODE] [MIGRATION]` separada siempre que cambia el schema, apuntando a un archivo versionado en `apps/functions/src/database/migrations/` (generado por `drizzle-kit generate`). Su `VERIFY` registra dos comandos aprobados por `check_database_safety.mjs`: uno aplica la migración en la base de **prueba**, otro consulta el estado de las migraciones;
   - una tarea `[DOC]` para `.fireskills/STACK.md` cuando cambian los manifests o la estructura, y para `.fireskills/DATABASE.md` cuando cambia la base de datos;
   - para una pantalla: tareas para cada pantalla, menús, formularios y acciones, en una subsección `#### Fase de interface`, y una tarea que actualiza `.fireskills/INTERFACE.md`. Toda tarea que escribe un `.vue` con componentes `U*` lista `$fireskill-specialist-nuxt-ui` en `PREP`.
6. Valida:

   ```bash
   node fireskills/skills/fireskill-05-tasks/scripts/validate_tasks.mjs specs/defined/<NNNN>-<slug>/spec.md --allow-draft
   node fireskills/skills/fireskill-05-tasks/scripts/validate_interface_tasks.mjs specs/defined/<NNNN>-<slug>/spec.md
   ```

   El segundo se ejecuta cuando la entrega tiene pantalla. Hasta tres ciclos de corrección.
7. Mientras `Plan Gate: Pending`, pasa el turno a `$fireskill-06-tdd-bdd` en modo `prepare` para escribir la primera prueba que falla (consulta el [Paso 6](/docs/fireskills/getting-started/step-tdd-bdd)), y luego retoma: `Plan Gate: Passed`, `Status: Planned`, resultado escrito en la sección 13, y `bun run fireskill transition <id> planned`.

Si la validación falla, la spec sigue en `Defined` con `Plan Gate: Failed`, y el agente informa qué la bloquea.

## Resultado

Un `spec.md` en `specs/planned/<NNNN>-<slug>/` con la lista completa de tareas, ordenada por dependencia, y `Plan Gate: Passed`.
