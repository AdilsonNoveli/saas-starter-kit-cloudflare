**Skill:** `fireskill-06-tdd-bdd` · **Hace preguntas:** no · **Crea:** archivos de prueba Vitest junto al código; actualiza la tabla de evidencia del `spec.md`

## Cuándo usarlo

Normalmente no la llamas tú: `$fireskill-05-tasks` la llama en modo `prepare`. Llámala tú mismo cuando quieras una prueba fallida más, un `cycle` o una auditoría.

## Qué escribir

```text
Use $fireskill-06-tdd-bdd para ler o Gherkin de referência em specs/<estado>/<NNNN>-<slug>/spec.md, criar testes TDD rastreáveis e executar RED-GREEN-REFACTOR sem executar .feature. Orquestre transições automáticas com anúncio, execução e retomada na mesma conversa.
```

Puedes indicar el modo en el mismo mensaje: `prepare`, `cycle` o `verify`.

## Los tres modos

| Modo | Cuándo | Qué hace |
|---|---|---|
| `prepare` | antes de la implementación (spec `Defined`, `Plan Gate: Pending`) | escribe la siguiente prueba y demuestra el RED, **sin** código de producción; marca como hecha solo esa tarea `[TEST]`; vuelve a `$fireskill-05-tasks` |
| `cycle` | durante la implementación (spec `Planned` o `Implementing`) | RED → GREEN → REFACTOR para una porción elegida |
| `verify` | en cualquier momento | ejecuta las suites y audita la trazabilidad, sin crear comportamiento nuevo |

Si no lo indicas, usa `prepare` cuando la lista de tareas aún no se está ejecutando y `cycle` cuando hay una tarea activa.

## Cómo se escribe una prueba

- El bloque Gherkin del `AC` en `spec.md` es la referencia. **No se crea ni se ejecuta ningún archivo `.feature`.**
- Las pruebas son Vitest, junto al código en su layer (`shared/**/*.test.ts` o `server/**/*.test.ts`), en el nivel más bajo que demuestre el comportamiento. Ejemplos reales: `layers/teams/shared/utils/abilities.test.ts`, `layers/teams/server/utils/team-seats.test.ts`.
- Cada caso ejecutable lleva su propio marcador, justo al lado de su definición:

  ```ts
  // SPECSFY: US-001 FR-001 AC-001
  it("rejeita convite de quem não é administrador", async () => {
    // …
  });
  ```

- Al menos **tres casos distintos** para la funcionalidad completa y para cada `US`, `FR` y `NFR`: camino feliz, regla o variación crítica, fallo o límite relevante. Un marcador compartido por un archivo entero cuenta como un caso.
- Todo `AC` está cubierto por al menos un caso.

## RED, GREEN, REFACTOR

1. **RED**: escribe la prueba más pequeña que demuestre el `AC`, ejecútala (`bun run test`, o `bunx vitest run <file>`) y confirma que falla **porque el comportamiento no existe**. Un fallo por sintaxis, import, fixture o entorno no cuenta. Una prueba que pasa antes del cambio no demuestra nada y hay que refinarla.
2. **GREEN** (en `cycle`): el mínimo código de producción, primero la prueba focal, luego la suite relacionada.
3. **REFACTOR**: limpia el código con las pruebas en verde.

Cada paso se registra en la tabla `Evidência RED-GREEN-REFACTOR` de la spec.

## Protección de la base de datos

Antes de que se ejecute cualquier prueba, `check_database_safety.mjs` clasifica el comando. Si no es `SAFE`, no se ejecuta ninguna prueba y el paso queda pendiente. Las pruebas que llegan a PostgreSQL necesitan una base de datos de prueba dedicada; usa una transacción revertida o fixtures limitados al caso.

## Comprueba tú mismo la trazabilidad

```bash
node fireskills/skills/fireskill-06-tdd-bdd/scripts/check_traceability.mjs specs/planned/<NNNN>-<slug>/spec.md .
bun run test
```
