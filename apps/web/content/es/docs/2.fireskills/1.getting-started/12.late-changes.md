**Skill:** `fireskill-update-spec` · **Hace preguntas:** solo cuando las opciones cambian el resultado de forma material · **Modifica:** el `spec.md` y solo los gates que el cambio invalida

## Cuándo usarlo

Una spec ya pasó el Definition Gate (está `Defined`, `Planned`, `Implementing`, `Reviewing` o `Complete`) y quieres añadir, quitar, corregir o cambiar algo. Para una spec que sigue en `Draft` y nunca pasó el gate, usa el [Paso 3: Specify](/docs/fireskills/getting-started/step-specify).

## Qué escribir

```text
Use $fireskill-update-spec para incorporar este novo pedido à especificação existente e orquestrar transições automáticas até a retomada.

specs/planned/0001-convite-de-membros-por-e-mail/spec.md
O link do convite agora expira em 24 horas, não em 48.
```

## Qué hace el agente

1. Conserva tu petición palabra por palabra antes de interpretarla, luego localiza la spec y lee la cabecera, los requisitos, los escenarios, el plan, las tareas, los gates y la evidencia. Los cambios que ya existan en Git en la spec no se atribuyen a tu petición.
2. **Clasifica** el cambio antes de escribir:

   | Cambio | Qué hace |
   |---|---|
   | interno, reversible, sin efecto observable | no toca la spec; registra la evaluación en la evidencia de la tarea y retoma la implementación |
   | editorial, mismo sentido | edita solo la redacción; mantiene estado y gates |
   | comportamiento, aceptación, alcance, datos, seguridad o interfaz | reabre desde el **Acto I**: `Status: Draft`, los tres gates `Pending` |
   | solo solución, tareas o estrategia de pruebas | reabre desde el **Acto II**: `Status: Defined`, el `Definition Gate` sigue `Passed`, `Plan Gate` y `Delivery Gate` vuelven a `Pending` |
   | una capacidad nueva e independiente | no la añade en silencio: va a `$fireskill-02-backlog` o `$fireskill-03-specify` |

3. Edita solo el `spec.md` (y el `research/` indexado). Mantiene los IDs existentes y nunca renumera. Para un cambio de comportamiento, registra motivo, decisión e IDs impactados en la sección 17. Nunca crea `change-request.md` ni ningún archivo paralelo.
4. Proyecta el impacto (solo lectura):

   ```bash
   node fireskills/skills/fireskill-update-spec/scripts/analyze_change.mjs specs/<state>/<NNNN>-<slug>/spec.md --base HEAD --mode impact
   ```

   `--mode changelog` lista los IDs añadidos, eliminados y modificados.
5. Ejecuta la validación estructural (`validate_spec.mjs … --allow-draft`) y **retoma** el flujo:
   - cambio desde el Acto I: `$fireskill-04-validate`, luego tareas, TDD/BDD y el paso que originó el cambio;
   - cambio solo en el Acto II: `$fireskill-05-tasks`, que reconcilia el plan, llama a `$fireskill-06-tdd-bdd` y retoma;
   - cambio encontrado durante la implementación: `$fireskill-07-implement` retoma solo cuando los Definition y Plan Gates vuelven a `Passed` y existe un RED válido para el comportamiento nuevo;
   - cambio después de `Complete`: los actos invalidados se ejecutan de nuevo y `Complete` solo vuelve con el Delivery Gate y la Definition of Done demostrados; la spec vuelve primero a `review`.

La evidencia histórica nunca se reescribe como si se hubiera producido para la nueva petición: la prueba que depende de la versión invalidada se marca como pendiente.

## Los movimientos de carpeta

`bun run fireskill transition` permite retroceder un paso (`completed` → `review`, `review` → `in-progress`, `in-progress` → `planned`, `planned` → `defined`, `defined` → `draft`), nunca saltando. La skill lo usa según haga falta.
