La metodología de Fireskills organiza todo el trabajo de ingeniería en **Tres Actos**. Cada Acto representa una mentalidad, un conjunto de herramientas y un umbral de validación distintos, de modo que la implementación nunca empiece sin requisitos claros y contratos de prueba demostrados.

```text
┌──────────────────────────────────────┐
│            ACT I: DEFINE             │
│ • User Stories (US)                  │
│ • Requirements (FR/NFR)              │
│ • Gherkin BDD Scenarios              │
│ ──> Definition Gate: Passed          │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│        ACT II: DESIGN & PROVE        │
│ • Task Decomposition & 6-Step List   │
│ • Executable TDD Tests               │
│ • Observed RED State                 │
│ ──> Plan Gate: Passed                │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│           ACT III: DELIVER           │
│ • RED -> GREEN Implementation        │
│ • Visual Inspection against Tokens   │
│ • Full Regression & Documentator     │
│ ──> Delivery Gate: Passed            │
└──────────────────────────────────────┘
```

---

## Acto I: Definir

**Objetivo**: Establecer qué hay que construir, por qué importa, a quién sirve y qué criterios definen el éxito.

### Actividades:
- **Recepción y aclaración del alcance**: Traer las peticiones en bruto de `specs/inbox/` a `specs/backlog/`.
- **Descubrimiento con las partes interesadas**: Llevar a cabo una indagación estructurada mediante el Contrato de Preguntas Numeradas para resolver ambigüedades y casos límite.
- **Redacción de la especificación**: Documentar Historias de Usuario (`US`), Requisitos Funcionales (`FR`) y Requisitos No Funcionales (`NFR`).
- **Escenarios BDD en Gherkin**: Formular especificaciones de comportamiento legibles por humanos (`Given / When / Then`) directamente en el `spec.md`.
- **Descubrimiento de UI y datos**: Especificar las pantallas afectadas, entradas, estados de error y modificaciones de schema.

### Umbral de salida:
El Acto I solo termina cuando el **Definition Gate** se marca formalmente como `Passed`.

---

## Acto II: Diseñar y Probar

**Objetivo**: Formular el plan técnico y demostrar que nuestra comprensión es correcta, estableciendo pruebas que fallan (RED) antes de escribir cualquier código de aplicación.

### Actividades:
- **Descomposición en tareas**: Dividir la spec en tareas atómicas y secuenciadas dentro del `spec.md`. Cada tarea debe seguir el checklist obligatorio de 6 ítems (`PREP`, `EXECUTE`, `VERIFY`, `VISUAL`, `EVIDENCE`, `IMPROVE`).
- **Alineación arquitectónica**: Seleccionar los patrones técnicos adecuados, garantizando compatibilidad con las restricciones de Cloudflare Workers.
- **Derivación de pruebas TDD**: Derivar suites de prueba Vitest ejecutables directamente de los escenarios Gherkin de referencia. Todo caso ejecutable lleva su propio marcador `// SPECSFY:`.
- **Observación de un RED válido**: Ejecutar la suite de pruebas (`bun run test`) y observar que las pruebas fallan estrictamente porque la funcionalidad aún no está implementada, y no por errores de sintaxis o de entorno.

### Umbral de salida:
El Acto II solo termina cuando el **Plan Gate** se marca formalmente como `Passed`.

---

## Acto III: Entregar

**Objetivo**: Implementar código de nivel de producción, hacer que las pruebas pasen (GREEN), realizar revisiones visuales y empaquetar la prueba verificada.

### Actividades:
- **RED → GREEN → REFACTOR**: Escribir código mínimo y limpio para poner en verde las pruebas que fallan. Refactorizar por claridad, rendimiento y adherencia a los patrones de la stack.
- **Verificación de diseño visual**: Inspeccionar las interfaces renderizadas en viewports de escritorio y móvil contra `.specsfy/DESIGNSYSTEM.MD`, verificando tipografía, espaciado, padding, bordes y accesibilidad.
- **Suite de regresión**: Ejecutar las suites de pruebas completas y los verificadores de tipos (pruebas desde la raíz; tipos desde `apps/app`):
  ```bash
  bun run test                       # repository root
  cd apps/app
  bun run typecheck
  bunx vue-tsc --noEmit -p server/tsconfig.json
  ```
- **Sincronización de contexto y documentación**: Actualizar los archivos de contexto de `.specsfy` (`DATABASE.md`, `INTERFACE.md`) y ejecutar `fireskill-documentator`.

### Umbral de salida:
El Acto III solo termina cuando el **Delivery Gate** se marca formalmente como `Passed` y la especificación pasa a `completed`.

---

## Reabrir actos por cambio de requisitos

Si los requisitos cambian a mitad del ciclo, los gates posteriores no pueden seguir siendo válidos:
- **Cambio de requisito o de comportamiento**: Reabre los Actos I, II y III. El Definition Gate y el Plan Gate vuelven a `Pending`.
- **Cambio en el plan técnico**: Reabre los Actos II y III. El Definition Gate sigue `Passed`, mientras que el Plan Gate vuelve a `Pending`.
