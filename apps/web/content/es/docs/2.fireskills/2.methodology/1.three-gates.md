Los gates de calidad se registran en la cabecera de la spec, en los campos `Definition Gate`, `Plan Gate` y `Delivery Gate`. Una skill solo define un gate con la evidencia que ese gate exige; un gate posterior nunca sigue aprobado sobre un gate anterior invalidado.

```markdown
| Campo | Valor |
| --- | --- |
| Status | Implementing |
| Definition Gate | Passed |
| Plan Gate | Passed |
| Delivery Gate | In Progress |
```

Valores que se ven en el flujo: `Pending` (no evaluado), `Passed`, `Failed` (la última comprobación no pasó) y, para el Delivery Gate mientras el trabajo está en curso, `In Progress`.

---

## 1. Definition Gate (cierra el Acto I)

Responsable: `$fireskill-04-validate`. El resultado `READY` define `Definition Gate: Passed` y `Status: Defined`; `NOT READY` define `Failed` y mantiene `Draft`.

Qué exige:

1. **Formato**: `Formato: Specsfy/2.0`, los tres actos en orden, slug igual al directorio, paquete solo con `spec.md` y `research/` opcional.
2. **Cobertura**: al menos **tres `AC` distintos** para la funcionalidad completa y para cada `US`, `FR` y `NFR`, contados solo cuando el `AC` declara el ID en `**Cobre**`.
3. **Escenarios**: Gherkin Given/When/Then en la spec, asociados a los requisitos.
4. **Interfaz** (cuando `Interface para pessoas: Sim`): sección 10 con stack, pantallas, flujo de información, menús, formularios y acciones, composición, componentes, estados y accesibilidad. Un CRUD debe declarar `PageHeader`, `UTable`, la columna `ID`, editar y borrar.
5. **Datos y contexto**: un cambio de stack o de persistencia debe constar en la Definition of Done para `.fireskills/STACK.md` o `.fireskills/DATABASE.md`.
6. **Validador estructural**: `node fireskills/skills/fireskill-04-validate/scripts/validate_spec.mjs specs/<state>/<NNNN>-<slug>/spec.md` (con `--allow-draft` mientras siga en `Draft`).

`bun run fireskill validate` es un linter rápido que también puedes ejecutar, pero no es este gate. Consulta el [Paso 4](/docs/fireskills/getting-started/step-validate).

## 2. Plan Gate (cierra el Acto II)

Responsables: `$fireskill-05-tasks` y `$fireskill-06-tdd-bdd`. `Plan Gate: Passed` define `Status: Planned`.

1. Tareas atómicas en la sección 14 con el checklist de seis ítems (`PREP`, `EXECUTE`, `VERIFY`, `VISUAL`, `EVIDENCE`, `IMPROVE`).
2. Una tarea `[TEST] [TDD]` por `AC`; toda tarea `[CODE]` depende de su predecesor TDD.
3. Casos Vitest ejecutables, cada uno con su propio marcador `// SPECSFY:`, al menos tres por funcionalidad/`US`/`FR`/`NFR`.
4. Un **RED válido** observado: las pruebas fallan porque el comportamiento no existe, no por sintaxis o entorno.
5. Una tarea `[CODE] [MIGRATION]` para todo cambio de schema.
6. `validate_tasks.mjs` (y `validate_interface_tasks.mjs` para pantallas) pasan sin `--allow-draft`.

## 3. Delivery Gate (cierra el Acto III)

Responsable: `$fireskill-07-implement`, con la aceptación final por `$fireskill-04-validate`. `Delivery Gate: Passed` define `Status: Reviewing`; la aceptación mueve entonces la spec a `completed` con `Status: Complete`.

1. Todas las tareas de la sección 14 marcadas, con evidencia para cada una.
2. Suite completa en verde: `bun run test` (raíz del repositorio).
3. Tipos limpios: en `apps/app`, `bun run typecheck` y `bunx vue-tsc --noEmit -p server/tsconfig.json`.
4. Trazabilidad: todo `AC`, `FR`, `NFR` e ítem de la Definition of Done tiene evidencia actual; sin tareas abiertas, placeholders ni pruebas omitidas.
5. `VISUAL` hecho en toda tarea con pantalla.
6. Monitor de contexto sin `PENDING`, y `build_documentation.mjs --check` pasando.
7. Para cada `[MIGRATION]`: el archivo, el comando que la aplicó en la base de **prueba** y la consulta de estado.
8. Para cambios en `apps/functions` o `layers`, un `sst deploy` real es la comprobación que importa. Necesita tu autorización explícita; el flujo no lo ejecuta por su cuenta.

---

## Invalidación

- Un cambio de requisitos, escenarios, alcance, datos, seguridad o interfaz devuelve la spec a `Draft`: los tres gates vuelven a `Pending`.
- Un cambio solo de tareas, solución o estrategia de pruebas la devuelve a `Defined`: el `Definition Gate` sigue `Passed`; `Plan Gate` y `Delivery Gate` vuelven a `Pending`.

Estos movimientos los hace `$fireskill-update-spec`. Consulta [Cambios tardíos](/docs/fireskills/getting-started/late-changes).
