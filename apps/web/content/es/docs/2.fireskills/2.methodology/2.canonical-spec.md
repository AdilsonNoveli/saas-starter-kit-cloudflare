`specs/<state>/<NNNN>-<slug>/spec.md` es la única fuente normativa de una porción de trabajo. Los archivos paralelos `plan.md`, `tasks.md`, `research.md` y `data-model.md` no se usan. El archivo se crea a partir de la plantilla `fireskills/skills/templates/Spec.md` con `iniciar_spec.mjs`; no lo escribes desde cero.

---

## Estructura de directorios

```text
specs/
├── inbox/
│   └── 2026-09-18-174245-convite-de-membros-por-e-mail.md
├── backlog/
│   └── 0001-convite-de-membros-por-e-mail.md
├── milestones/            (only when an MVP is imported)
├── draft/
├── defined/
├── planned/
├── in-progress/
├── review/
└── completed/
    └── 0001-convite-de-membros-por-e-mail/
        ├── spec.md
        └── research/      (optional)
```

- `inbox/` y `backlog/` guardan notas y briefs; no son normativos.
- Una spec existe en exactamente una carpeta de estado; la carpeta es el estado operativo.
- `research/` guarda solo evidencia que realmente se consultó (copias, snapshots, contratos, ejemplos) y se indexa dentro de `spec.md`. No guarda código de producción ni pruebas.
- No se permite nada más en el paquete de la spec.

## La cabecera

Una tabla Markdown de dos columnas, `Campo` / `Valor` (no la conviertas en líneas `**Campo**: valor`). Salida real de `iniciar_spec.mjs`:

```markdown
# Especificação integrada: Convite de membros por e-mail

| Campo | Valor |
| --- | --- |
| Formato | Specsfy/2.0 |
| ID | SPEC-0001 |
| Slug | 0001-convite-de-membros-por-e-mail |
| Status | Draft |
| Effort | 1 |
| Effort updated at | 2026-09-18 |
| Effort rationale | Estimativa inicial; revisar durante a descoberta. |
| ClickUp Task | |
| Milestones | |
| Definition Gate | Pending |
| Plan Gate | Pending |
| Delivery Gate | Pending |
| Evidence Contract | 1 |
| Interface para pessoas | A definir |
| Atualizada em | 2026-09-18 |
```

`Status` sigue a la carpeta: `Draft`, `Defined`, `Planned`, `Implementing`, `Reviewing`, `Complete`. `Interface para pessoas` es `Sim` o `Não`; `Sim` hace obligatoria la sección 10.

## Los tres actos y las 18 secciones

| Acto | Secciones |
|---|---|
| **Ato I — Definir** | 1 Problema e resultado · 2 Research e esclarecimentos · 3 Escopo e atores · 4 Princípios e restrições do projeto · 5 Histórias de usuário · 6 Cenários BDD de aceite · 7 Requisitos |
| **Ato II — Projetar e provar** | 8 Plano técnico · 9 Modelo de dados · 10 Interfaces e contratos · 11 Estratégia TDD · 12 Plano de testes e rastreabilidade · 13 Validações · 14 Tarefas · 15 Ordem de execução |
| **Ato III — Entregar e validar** | 16 Dependências, riscos e suposições · 17 Decisões · 18 Definition of Done |

Los IDs tienen tres dígitos y nunca se renumeran: `US-001`, `FR-001`, `NFR-001`, `AC-001`, `DEC-001`, tareas `T001`.

### Escenarios (sección 6)

Cada `AC` es un encabezado, una línea `**Cobre**` con los IDs que cubre y un bloque Gherkin:

````markdown
#### AC-001 — [comportamento]

**Cobre**: US-001, FR-001, NFR-001

```gherkin
@US-001 @FR-001 @NFR-001 @AC-001
Feature: [capacidade observável]

  Scenario: [caminho feliz aceito]
    Given [estado inicial]
    When [ação]
    Then [resultado observável]
```
````

El Gherkin vive solo aquí. No se crea ni se ejecuta ningún archivo `.feature`.

### Interfaz (sección 10)

Cuando hay una pantalla: stack y convenciones, pantallas y responsabilidades, flujo de información y navegación, menús, formularios y acciones, composición, los componentes Vue y `@nuxt/ui` elegidos, estados y accesibilidad, el contrato de CRUD (`PageHeader`, `UTable` con `enterpriseTableUi`, `ID` visible, enlace en la fila, editar y borrar) y la revisión visual.

### Tareas (sección 14)

```markdown
- [ ] T001 [TEST] [TDD] [US-001] Derivar teste Vitest do BDD em layers/teams/shared/utils/abilities.test.ts — Refs: FR-002, AC-003 — Depends: none
  - [ ] **PREP**: …
  - [ ] **EXECUTE**: …
  - [ ] **VERIFY**: …
  - [ ] **VISUAL**: …
  - [ ] **EVIDENCE**: …
  - [ ] **IMPROVE**: …
```

Un cambio en la base de datos incluye una tarea `[CODE] [MIGRATION]` que apunta a un archivo versionado en `apps/functions/src/database/migrations/`.

### Pruebas y trazabilidad (secciones 11–12)

Cada caso Vitest ejecutable lleva su propio marcador junto a su definición:

```ts
// SPECSFY: US-001 FR-001 AC-001
```

El marcador es un comentario; no forma parte del título de la prueba. La tabla `Evidência RED-GREEN-REFACTOR` registra cada RED y GREEN observado.

---

## Antipatrones

- Crear `plan.md`, `tasks.md`, `todo.md` o cualquier otro archivo paralelo.
- Pruebas sin marcador `// SPECSFY:`, o un marcador compartido por un archivo entero (cuenta como un caso).
- Una tarea sin los seis ítems del checklist, o sin el `VISUAL`.
- Dejar ejemplos de la plantilla, `TBD` o `TODO` en una spec marcada como `Defined`.
