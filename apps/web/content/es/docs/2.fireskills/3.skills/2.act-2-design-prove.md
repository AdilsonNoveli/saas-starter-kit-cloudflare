El Acto II convierte la spec definida en un plan y lo demuestra con pruebas que fallan por el motivo correcto. Termina en el **Plan Gate**.

| Skill | Crea o modifica | Página del paso |
|---|---|---|
| `fireskill-05-tasks` | las secciones 14 y 15 del `spec.md`; la mueve a `specs/planned/` | [Paso 5](/docs/fireskills/getting-started/step-tasks) |
| `fireskill-06-tdd-bdd` | archivos de prueba Vitest junto al código; la tabla de evidencia de la spec | [Paso 6](/docs/fireskills/getting-started/step-tdd-bdd) |

## `fireskill-05-tasks`

Exige `Definition Gate: Passed` y `Status: Defined`. Reemplaza solo las secciones 14 y 15 del mismo `spec.md`. Formato de la tarea:

```markdown
- [ ] T002 [CODE] [US-001] Implementar validação em layers/teams/server/trpc/teams.ts — Refs: FR-002, AC-003 — Depends: T001
```

Etiquetas después del ID: `[P]`, `[TEST]`, `[TDD]`, `[CODE]`, `[DOC]`, `[OPS]`, `[US-NNN]`, y `[MIGRATION]` junto con `[CODE]` u `[OPS]`. Toda tarea tiene el checklist `PREP`, `EXECUTE`, `VERIFY`, `VISUAL`, `EVIDENCE`, `IMPROVE`, en ese orden. Validadores: `validate_tasks.mjs` y, para pantallas, `validate_interface_tasks.mjs`.

## `fireskill-06-tdd-bdd`

Modos `prepare` (primer RED, sin código de producción), `cycle` (RED → GREEN → REFACTOR) y `verify` (suites y trazabilidad). El Gherkin de la spec es la referencia; no existe ningún archivo `.feature`. Todo caso ejecutable lleva su propio marcador como comentario al lado:

```ts
// SPECSFY: US-001 FR-001 AC-001
```

Al menos tres casos distintos para la funcionalidad y para cada `US`, `FR` y `NFR`. Las pruebas son Vitest (`bun run test`), y no se ejecuta ninguna prueba a menos que `check_database_safety.mjs` clasifique el comando como `SAFE`. Trazabilidad: `check_traceability.mjs`.

## Sellar el Plan Gate

`$fireskill-05-tasks` define `Plan Gate: Passed`, `Status: Planned` y ejecuta `bun run fireskill transition <id> planned`. Consulta [Gates de calidad](/docs/fireskills/methodology/three-gates).
