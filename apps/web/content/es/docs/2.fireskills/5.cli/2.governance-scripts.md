Son scripts de las skills (en `fireskills/skills/`), que se ejecutan con `node`. El flujo los ejecuta por ti; tú también puedes ejecutarlos.

---

## Monitor de contexto: `monitor_context.mjs`

```bash
node fireskills/skills/fireskill-setup/scripts/monitor_context.mjs --project . --check
```

Mira los archivos que cambiaste y aún no has confirmado con commit (`git diff`, staged y sin seguimiento; ignora `_docs/`, `fireskills/`, los archivos de contexto y los archivos de prueba) y lista qué documento de `.specsfy/*` exige cada cambio. Las reglas y la tabla completa están en [Contexto del proyecto](/docs/fireskills/getting-started/project-context).

La salida es `Context monitor: CURRENT`, o `Context monitor: PENDING` seguido de una línea por documento, por ejemplo:

```text
- .specsfy/DATABASE.md via $fireskill-aux-database: persistência alterada (apps/functions/src/database/migrations/0001_x.sql)
```

Opciones: `--json`, `--paths <files…>`, `--acknowledge-project-no-change`, `--acknowledge-rules-no-change`. El flujo trata `PENDING` como un bloqueo para cerrar una tarea y para el Delivery Gate.

## Guard de la base de datos: `check_database_safety.mjs`

```bash
node fireskills/skills/fireskill-setup/scripts/check_database_safety.mjs --project . --command "<command to check>"
```

Clasifica un comando antes de que el flujo lo ejecute. `SAFE` lo deja ejecutarse. Los comandos destructivos se clasifican como `IGNORED` y nunca se ejecutan, **aunque tú los apruebes**:

- `drizzle-kit push --force`, `drizzle-kit drop`
- `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `migrate:rollback`
- `db:wipe`, `schema:drop`, `prisma migrate reset`
- `DROP DATABASE`, `DROP SCHEMA`, `DROP TABLE`, `TRUNCATE`
- `RefreshDatabase`, `DatabaseMigrations` y equivalentes

Las pruebas que tocan PostgreSQL también necesitan una base de datos de prueba distinta de la que está en los secrets del stage (`DATABASE_HOST`, `DATABASE_NAME`…). Mientras esa separación no esté demostrada, no se ejecuta ninguna prueba así. Las 131 pruebas de Vitest existentes (billing, asientos de equipo, abilities) sustituyen `useDB` y no tocan una base de datos. Las pruebas que sí necesitan una base de datos usan una transacción revertida o fixtures limitados al caso.

## Comprobación del repositorio: `verify_repo.mjs`

```bash
node fireskills/skills/fireskill-04-validate/scripts/verify_repo.mjs .
```

Valida toda spec de `specs/` con los scripts de los Actos I a III y comprueba el contrato de toda skill `fireskill-*`: `SKILL.md` con un `name` coincidente, un `agents/openai.yaml`, menos de 500 líneas, y los recuentos esperados de skills base y auxiliares. Imprime `Specsfy verify: PASSED` o `FAILED`.
