**Onde criar o token**: na barra lateral do painel da Cloudflare, **Manage Account → Account API Tokens** → **"+ Create Token"** → **"Create Custom Token"**. (Não `dash.cloudflare.com/profile/api-tokens` — essa é a página de tokens pessoais do usuário, uma lista diferente da de tokens pertencentes à conta que este projeto utiliza.)

Já tem um token de uma configuração anterior e só precisa adicionar a permissão `D1` a ele? Abra **Manage Account → Account API Tokens**, clique no nome do token para editá-lo, clique na linha da política delimitada para **"Entire Account"** e continue a partir do passo 3 abaixo. Falta `DNS` ou `Page Rules`? No mesmo lugar, mas clique na linha da política delimitada para **o seu domínio** e continue a partir do passo 2.

Na tela de políticas (o layout muda ocasionalmente — use a caixa **"Search for a permission group..."** se não encontrar algo por categoria):

1. Mantenha ou renomeie o nome do token e clique em **Edit Cloudflare Workers**:

   ![Nome do token](/images/docs/token-name-cloudflare.webp)
   ![Editar Cloudflare Workers](/images/docs/Edit-Cloudflare-Workers.webp)

2. Na primeira política, clique em **"All zones ... Account"** para adicionar uma segunda política vinculada a uma **zona** (o Workers Custom Domains requer isso separadamente da política de conta):
   - Mude o escopo dessa política para **"Specified Domains"** e escolha o seu domínio:

     ![Domínios especificados](/images/docs/pecified-domains.webp)

   - Marque **Edit** em cada uma destas três. Pesquise uma por vez — elas ficam em categorias diferentes:

     | Permissão | Por que o deploy precisa dela |
     | --- | --- |
     | `Workers Routes` | Vincula o seu domínio ao Worker (Workers Custom Domains). |
     | `DNS` | O estágio `production` também redireciona `www.<seu domínio>` para o domínio raiz, e o SST cria um registro DNS placeholder com proxy para isso. É a linha chamada apenas `DNS` ("Grants write access to DNS") em **DNS & Zones** — não as de conta "Account DNS Settings", "DNS Firewall" ou "DNS View". |
     | `Page Rules` | A regra de encaminhamento desse mesmo redirecionamento de `www`. |

     ![Workers Routes](/images/docs/Workers-Routes.webp)

     Estágios de desenvolvimento não criam o redirecionamento de `www`, mas o token é compartilhado, então conceda as três de uma vez. `DNS` e `Page Rules` são permissões de zona: elas vão somente nesta política do domínio — a política **"Entire Account"** do passo 3 não precisa delas.

3. Em uma segunda política delimitada para **"Entire Account"**, adicione no mínimo (pesquise cada termo e marque **Edit** — não há problema se mais itens vierem marcados por padrão):
   - `Workers Scripts`
   - `Workers KV`
   - `Workers R2`
   - `Queues`
   - `Hyperdrive`
   - `D1` — listado sob a categoria **Developer Platform** após a busca (não junto de Workers/KV/R2 sob Account), descrito como "Grants write access to D1 configuration and SQL queries". Dá suporte ao banco de dados de conteúdo do site de documentação (caixa de pesquisa de `apps/web`). A ausência disso faz o deploy falhar com `401 Unauthorized` no recurso `D1Database` especificamente, enquanto todos os outros recursos ainda são implantados normalmente.

   Confirme se todas as permissões estão definidas como Edit:

   ![Editar permissões de conta](/images/docs/edit-account.webp)

4. Clique em **"Review token"** e depois em **"Create Token"**:

   ![Revisar token](/images/docs/Review-token.webp)
   ![Criar token](/images/docs/create-token.webp)

5. Guarde o token em um local seguro. O que você realmente usará daqui para frente são o **API token** e o **Account ID**:

   ![Tokens](/images/docs/tokens.png)

Copie o valor do token agora — ele só é exibido uma vez.

Mantenha ambos os valores à mão: eles precisam ser uma **variável de ambiente** real ([próximo passo](/docs/saas-starter-kit/getting-started/secrets)) *e* entrar no arquivo `.env` que você carrega no cofre de secrets. São as únicas duas variáveis que precisam de ambos.

Mais um requisito a nível de conta antes de fazer o deploy: o subdomínio `workers.dev` da sua conta já deve estar provisionado — abra **Workers & Pages** no painel da Cloudflare uma vez (ele é criado automaticamente na primeira vez que essa seção é carregada). Pule isso em uma conta nova e o primeiro deploy falhará no meio do processo com `403: "You need a workers.dev subdomain..."` (código de erro 10063) — o token e o account ID estão corretos, mas esta é uma etapa única de configuração da conta que não tem relação com nenhum dos dois.

**Erros de deploy que vêm do token ou da zona**, e o que cada um significa:

| Erro na saída do deploy | Causa | Correção |
| --- | --- | --- |
| `403` código `10000` "Authentication error" em um `DnsRecord` | O token não tem `DNS` → Edit no seu domínio | Adicione-a (passo 2) |
| `403` código `9109` "Unauthorized to access requested resource" em um `PageRule` | O token não tem `Page Rules` → Edit no seu domínio | Adicione-a (passo 2) |
| `401 Unauthorized` em `D1Database` | O token não tem `D1` | Adicione-a (passo 3) |
| `409` código `100117` "already has externally managed DNS records" em `WorkersCustomDomain` | Não é permissão: o hostname já tem um registro A, AAAA ou CNAME | Apague esse registro em **DNS → Records** — no `production`, tanto o domínio raiz quanto o `www` — e faça o deploy de novo |

`bun run doctor -- --stage production` (executado automaticamente pelo `bun run deploy`) verifica as permissões `DNS` e `Page Rules` antes de publicar qualquer coisa e nomeia as que faltam.
