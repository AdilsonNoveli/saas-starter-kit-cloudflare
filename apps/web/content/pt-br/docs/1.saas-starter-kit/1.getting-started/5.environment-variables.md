Todas as variáveis abaixo vivem em `.env.example` (o modelo) e são carregadas no cofre de secrets do SST por estágio — consulte [Secrets](/docs/saas-starter-kit/getting-started/secrets) para os comandos de carregamento. Esta página é a referência de **onde cada valor é obtido**, uma plataforma por vez, para quem está configurando isso pela primeira vez.

Você não precisa de todas as linhas — preencha apenas o que um recurso que você realmente utiliza exige. Tudo o que não está marcado como **Sempre** é controlado por uma flag em `config.ts`; deixe em branco e desative a flag se não for usar essa integração.

## 1. Cloudflare — deploy authentication

Exigido antes de qualquer comando `sst` funcionar, em todas as máquinas que realizam deploys. O guia completo com capturas de tela (permissões, escopo do token) está em [Acesso à Cloudflare](/docs/saas-starter-kit/getting-started/cloudflare-access).

| Variable | Required | Get it at |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | Always | [dash.cloudflare.com](https://dash.cloudflare.com) → **Manage Account → Account API Tokens** → **Create Token**. Não é a página pessoal `profile/api-tokens` — ela lista outro tipo de token. |
| `CLOUDFLARE_ACCOUNT_ID` | Always | [dash.cloudflare.com](https://dash.cloudflare.com) → o menu **⋮** ao lado do nome da sua conta → **Copy Account ID** (também aparece na seção API da página Overview de qualquer domínio) |

## 2. Database — PostgreSQL

Qualquer Postgres padrão funciona — o aplicativo utiliza o protocolo de conexão nativo, nunca um SDK de provedor. Usando o [Supabase](https://supabase.com) como exemplo (é para onde o `.env.stage` deste projeto aponta):

| Variable | Required | Get it at |
|---|---|---|
| `DATABASE_HOST` | Always | [supabase.com/dashboard](https://supabase.com/dashboard/project/_/settings/database) → seu projeto → **Settings → Database** → aba **Direct connection**. Veja o aviso abaixo — não use a aba do pooler. |
| `DATABASE_PORT` | Always | Mesma aba (`5432`) |
| `DATABASE_NAME` | Always | Mesma aba |
| `DATABASE_USER` | Always | Mesma aba — apenas `postgres`, sem sufixo |
| `DATABASE_PASSWORD` | Always | Mesma aba — definida na criação do projeto; redefina-a lá se não a tiver |

### Use the Direct connection, not the Session pooler

A página de configurações de banco de dados do Supabase exibe dois modos de conexão. **Use a conexão Direct** — a [documentação oficial do Hyperdrive da Cloudflare é explícita sobre isso](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/): *"você deve usar a string de conexão Direct em vez das strings de conexão agrupadas (pooled), pois o Hyperdrive executará o agrupamento de conexões para garantir o acesso ideal a partir dos Workers."* O Hyperdrive já faz o pooling de conexões na borda da Cloudflare — roteá-lo pelo próprio pooler do Supabase (Supavisor) resultaria em pooling em cima de pooling, sem nenhum benefício.

**Os dois modos usam formatos de host e nome de usuário diferentes e não intercambiáveis — nunca misture o host de um modo com o usuário de outro:**

| | Host | User |
|---|---|---|
| **Direct** (use este) | `db.<project-ref>.supabase.co` | `postgres` |
| Session pooler (não use para `DATABASE_HOST`/`DATABASE_USER`) | `aws-0-<region>.pooler.supabase.com` | `postgres.<project-ref>` |

Combinar um host do modo direto com um usuário do modo pooler (ou vice-versa) não gera um erro óbvio de imediato — o deploy acontece e, em seguida, a Cloudflare rejeita com `Hyperdrive → 400: "Invalid database credentials"` (código de erro 2013), o que soa como senha incorreta mesmo quando a senha está certa.

**O único caso em que você ainda pode precisar do pooler:** todo deploy executa as migrações do banco automaticamente a partir da **sua própria máquina** (`infra/utils/nuxt.ts`, comando local), usando estes mesmos valores — e não a partir da borda da Cloudflare. A conexão direta do Supabase é exclusivamente IPv6. Se sua rede local não possuir uma rota IPv6 real para a internet, essa etapa local de migração falhará na conexão (timeout de conexão, e não o erro de credenciais acima), embora o Hyperdrive funcionasse perfeitamente a partir da rede IPv6 da Cloudflare. Se encontrar esse problema específico, alternar para o par do Session pooler (tabela acima) é a solução pragmática — você troca um pequeno overhead de duplo pooling pela conectividade da sua máquina local.

Usando RDS, Neon ou Postgres self-hosted: os mesmos cinco valores vêm da página de informações de conexão daquele provedor — a aplicação não se importa com qual seja, desde que a extensão `postgis` esteja habilitada (o Supabase a disponibiliza por padrão; execute `CREATE EXTENSION IF NOT EXISTS postgis;` em outros, se necessário).

## 3. Email — pick at least one provider

Ative/desative cada um em `config.ts` → `flags`. Apenas `resend` vem habilitado por padrão.

| Variable | Provider | Required when | Get it at |
|---|---|---|---|
| `RESEND_API_KEY` | Resend | `flags.resend` | [resend.com/api-keys](https://resend.com/api-keys) → **Create API Key** |
| `MAILGUN_API_KEY` | Mailgun | `flags.mailgun` | [app.mailgun.com](https://app.mailgun.com/) → **Settings → API Keys** |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Amazon SES | `flags.ses` | [console.aws.amazon.com/iam](https://console.aws.amazon.com/iam/home#/security_credentials) → crie um usuário IAM com permissão de envio SES → **Security credentials → Create access key**. Ainda não automatizado na infraestrutura (veja comentário em `infra/secret.ts`) — o usuário IAM deve ser criado manualmente. |
| `SPARKPOST_API_KEY` | SparkPost | `flags.sparkPost` | [app.sparkpost.com](https://app.sparkpost.com/) → **Account → API Keys** |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` | Generic SMTP | `flags.smtp` | Painel do seu provedor SMTP — não há um link único aqui, pois esse caminho aceita qualquer servidor SMTP |

## 4. Social login

Ambos são opcionais e alternados de forma independente (`flags.githubAuth`, `flags.googleAuth`). Cada URL de callback abaixo deve coincidir **exatamente**, incluindo o sufixo `/callback` — caso contrário, o provedor OAuth rejeitará o login com erro de incompatibilidade de URI de redirecionamento.

| Variable | Required when | Get it at |
|---|---|---|
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | `flags.githubAuth` | [github.com/settings/developers](https://github.com/settings/developers) → **New OAuth App**. Authorization callback URL: `https://auth.<your-domain>/github/callback` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | `flags.googleAuth` | [console.cloud.google.com/apis/credentials](https://console.cloud.google.com/apis/credentials) → **Create Credentials → OAuth client ID** (tipo: Web application). Authorized redirect URI: `https://auth.<your-domain>/google/callback` |

## 5. Payments

Stripe e Paddle podem estar ativos simultaneamente — uma linha de `Plan` apenas escolhe um provedor por registro (consulte [Pagamentos e Cobrança](/docs/saas-starter-kit/features/payments)).

| Variable | Required when | Get it at |
|---|---|---|
| `STRIPE_SECRET_KEY` | `flags.stripe` | [dashboard.stripe.com/apikeys](https://dashboard.stripe.com/apikeys) |
| `STRIPE_WEBHOOK_SECRET_KEY` | `flags.stripe` | [dashboard.stripe.com/webhooks](https://dashboard.stripe.com/webhooks) → **Add endpoint** → `https://app.<your-domain>/api/webhooks/stripe` → copie o **Signing secret** exibido |
| `PADDLE_API_KEY` | `flags.paddle` | [vendors.paddle.com/authentication](https://vendors.paddle.com/authentication) → **Developer Tools → Authentication → aba API keys** (testes em sandbox: [sandbox-vendors.paddle.com](https://sandbox-vendors.paddle.com/authentication)) |
| `PADDLE_WEBHOOK_SECRET` | `flags.paddle` | [vendors.paddle.com/notifications](https://vendors.paddle.com/notifications) → **New destination** → Webhook → `https://app.<your-domain>/api/webhooks/paddle` → copie a chave secreta exibida |
| `PADDLE_CLIENT_TOKEN` | `flags.paddle` | Mesma página de **Authentication** da `PADDLE_API_KEY` — aba **Client-side tokens**. Esta é pública por projeto (vai no bundle do navegador), mas ainda é definida por estágio como as demais. |

### PADDLE_API_KEY permissions — don't select "All"

Ao criar a chave de API, a aplicação acessa apenas dois recursos do Paddle no lado do servidor (`grep -rn "paddle\.\w*\.\w*(" apps/app/server` para verificar):

- **Customers** — **Read**. `paddle.customers.get(customerId)` no manipulador do webhook (`server/api/webhooks/paddle.post.ts`), para ler o e-mail do cliente.
- **Customer portal sessions** — **Write**. `paddle.customerPortalSessions.create(...)` (`server/trpc/routers/billing.ts`), para gerar o link do portal de faturamento que o cliente usa para gerenciar sua assinatura.

Nada mais — nenhuma permissão de Adjustments, Businesses, Addresses, Discounts, Products, Prices, Transactions ou Reports é usada em lugar algum do código. Uma chave com permissões mais amplas adiciona superfície de risco desnecessária caso vaze; amplie o escopo depois apenas se o novo código realmente chamar outro recurso do Paddle. (`paddle.webhooks.unmarshal(...)`, a terceira chamada ao SDK do Paddle no mesmo handler de webhook, valida a assinatura localmente — não faz chamada de rede e não precisa de permissão de API.)

## 6. Platform Admin console (/admin)

Não vêm de nenhuma plataforma externa — gere estas variáveis você mesmo, localmente. Consulte [Console de Platform Admin](/docs/saas-starter-kit/features/platform-admin) para saber o que elas protegem.

| Variable | Required | How to generate |
|---|---|---|
| `PLATFORM_MFA_SESSION_SECRET` | Always, before `/admin/*` works | `openssl rand -base64 32` (Git Bash/macOS/Linux) — ou PowerShell: `[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`. Seguro para rotacionar — no pior cenário, desconecta sessões elevadas ativas. |
| `PLATFORM_ADMIN_ENCRYPTION_KEY` | Always, before `/admin/*` works | Mesmo comando. **Não rotacione casualmente** — criptografa o segredo TOTP de cada administrador em repouso; rotacioná-la obriga todos os administradores cadastrados a configurar o MFA novamente. Guarde em local seguro (um gerenciador de senhas), não apenas neste arquivo. |

## 7. Two-factor authentication (regular users)

Mesmo comando de geração do par de platform admin acima, mesmas regras, mas mantidos em secrets separados — consulte [Console de Platform Admin](/docs/saas-starter-kit/features/platform-admin) para entender o motivo. Exigido apenas se um usuário ativar o 2FA em Configurações da Conta → Segurança; nada mais na aplicação depende destas variáveis.

| Variable | Required | How to generate |
|---|---|---|
| `USER_MFA_SESSION_SECRET` | Before any user can enable 2FA | `openssl rand -base64 32`. Seguro para rotacionar — no pior cenário, solicita um novo código aos usuários já cadastrados na próxima requisição. |
| `USER_MFA_ENCRYPTION_KEY` | Before any user can enable 2FA | Mesmo comando. **Não rotacione casualmente** — criptografa o segredo TOTP de cada usuário em repouso; rotacioná-la obriga todos que ativaram a reconfigurar o 2FA. |

## What never goes in this file

Variáveis `NUXT_PUBLIC_*`, URLs de workers, IDs de clientes expostos ao navegador e tudo o mais derivado no momento do deploy são computados automaticamente por `infra/*.ts` — nunca defina esses valores manualmente aqui. A única exceção: executar `seed/demo-accounts.ts` manualmente requer `AUTH_URL` e `AUTH_ADMIN_SECRET` no ambiente do seu terminal no momento da execução (não neste arquivo, não no cofre) — consulte [Console de Platform Admin](/docs/saas-starter-kit/features/platform-admin).
