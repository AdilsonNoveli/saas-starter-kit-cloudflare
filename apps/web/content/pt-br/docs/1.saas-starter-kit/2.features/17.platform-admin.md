`/admin` é um sistema de autoridade separado para o proprietário/operador do SaaS, e não para locatários (tenants). Ele **não** usa o RBAC por locatário que o restante da aplicação utiliza ([Controle de Acesso Baseado em Funções](/docs/saas-starter-kit/features/rbac)) — nada aqui tem escopo delimitado por equipe.

## Step-by-step: get your first platform-admin account

Não há formulário de cadastro para platform admins. É proposital — veja [Por que não há formulário de cadastro](#why-theres-no-signup-form) abaixo. Em vez disso: um usuário real se cadastra primeiro e depois é promovido por alguém com acesso ao banco de dados.

Faça isso uma vez **por ambiente** — uma vez para `stage`, uma vez para `production` — não uma vez por projeto.

**1. Faça o deploy com os dois secrets obrigatórios definidos.** Toda rota `/admin/*` recusa-se a funcionar sem ambos — ela falha fechada, nunca degrada para um modo inseguro:

```bash
sst secret set PLATFORM_MFA_SESSION_SECRET "$(openssl rand -base64 32)"
sst secret set PLATFORM_ADMIN_ENCRYPTION_KEY "$(openssl rand -base64 32)"
bun run deploy
```

**2. O futuro proprietário se cadastra como qualquer usuário normal** — via `/signup` ou provedor OAuth, escolhendo sua própria senha. Ninguém mais precisa saber dessa senha.

**3. Promova essa conta a platform admin.** Execute isto a partir de `apps/functions` (não na raiz do repositório — esse é o erro número 1 aqui), com os valores reais de `DATABASE_*` do estágio como variáveis de ambiente:

```bash
cd apps/functions
$env:DATABASE_HOST="..."
$env:DATABASE_PORT="5432"
$env:DATABASE_NAME="..."
$env:DATABASE_USER="..."
$env:DATABASE_PASSWORD="..."
bun run src/database/grant-platform-admin.ts --email=owner@yourdomain.com --role=SUPER_ADMIN
```

Isso só funciona se esse e-mail já tiver sido cadastrado no passo 2 — o script gera erro com `no user found` caso contrário. Ele nunca mexe em senhas, apenas cria uma linha na tabela `PlatformAdmin`. É um script manual por design, nunca executado automaticamente no deploy: uma concessão automatizada é exatamente como "uma variável de ambiente esquecida" se transforma em um super-admin permanente que ninguém lembra de ter criado.

**4. O proprietário faz login normalmente e visita `/admin`.** O aplicativo assume a partir daí: detecta que o MFA ainda não está configurado e abre a caixa de diálogo de cadastro automaticamente — um modal centralizado com fundo desfocado (o mesmo componente `AccountMfaSetupModal` usado na configuração de 2FA do usuário comum, apenas apontado para os endpoints `/api/admin/mfa/*`). Clique em "Generate code", escaneie o QR com qualquer aplicativo autenticador (Google Authenticator, 1Password, Authy...) e digite o código de 6 dígitos exibido. Pronto — a conta agora tem acesso total ao `/admin`.

### Why there's no signup form

Um formulário público de "torne-se o administrador" precisaria ficar exposto em uma URL pública antes que alguém fosse dono da plataforma — o que significa que quem descobrisse a URL primeiro assumiria o controle. Não há como protegê-lo nesse ponto, já que protegê-lo é todo o objetivo de existir um administrador. Promover uma conta pré-existente e já autenticada contorna o problema: a autoridade só é entregue a uma conta que já pertence comprovadamente a uma pessoa.

### Local development and demos only: seed both accounts at once

`seed/demo-accounts.ts` cria **ambas** as contas (o proprietário da plataforma e um cliente tenant de demonstração) em uma única chamada, com credenciais padrão conhecidas — conveniente para testar o produto de ponta a ponta, inadequado para qualquer ambiente que terceiros possam alcançar:

```bash
AUTH_URL=... AUTH_ADMIN_SECRET=... \
  bun run src/database/seed/demo-accounts.ts \
  --owner-email=owner@yourdomain.com --client-email=client@yourdomain.com \
  --owner-password=... --client-password=...
```

(`AUTH_URL`/`AUTH_ADMIN_SECRET` vêm do ambiente do shell, não do cofre — veja o comentário no cabeçalho do próprio script para saber onde lê-los de um estágio implantado). `--owner-email` e `--client-email` são obrigatórios — não existe endereço padrão, as contas são criadas em endereços reais seus. `--owner-password`/`--client-password` sobrescrevem os padrões descartáveis definidos em `parseArgs()` do script — se você executar isso contra um ambiente acessível por pessoas fora da sua equipe, sempre passe suas próprias senhas, nunca os padrões. Os padrões existem puramente para conveniência local/demo, porque foram feitos para serem descartáveis; deixados intactos em um ambiente público, tornam-se alvos imediatos de credential-stuffing.

## MFA after the first time: what to expect

Uma vez cadastrado, o `/admin` permanece acessível por 30 minutos por vez. Depois disso, visitar qualquer página de `/admin` reabre o mesmo modal desfocado — mas agora ele pede apenas um código de 6 dígitos novo em vez de exibir o QR code novamente. Não há nada para reescanear nem recadastrar.

Códigos incorretos sofrem limitação de taxa (10 tentativas a cada 5 minutos por conta) — se ficar bloqueado, aguarde alguns minutos antes de tentar novamente.

**Limitação conhecida:** perdeu seu autenticador? Não há recuperação self-service. Alguém com acesso ao banco de dados precisa limpar a coluna `mfaEnabledAt` desse administrador diretamente, e então você se cadastra novamente do zero da mesma forma — visite `/admin` e siga o modal de inscrição.

## What the console does

- **Empresas** (`/admin/companies`) — lista cross-tenant de todas as equipes, com busca, filtros de plano e status; suspenda e reative qualquer equipe. Todas as ações são explicitamente vinculadas ao ID da equipe, nunca às associações do próprio chamador.
- **Planos** (`/admin/plans`) — crie, edite, arquive/desarquive planos (o arquivamento é um soft delete: `Team.planId` e `Subscription.planId` são chaves estrangeiras reais, portanto uma linha de plano nunca é apagada fisicamente enquanto equipes a referenciarem). Também executa a configuração única de cancelamento do Stripe.
- **Fila (Queue)** (`/admin/queue`) — contadores de status de tarefas, mensagens em dead-letter com opção de reprocessamento e as últimas 20 linhas de log do cron. O processamento de tarefas é tratado como infraestrutura do próprio SaaS, e não como um recurso de locatário.
- **Log de Auditoria** (`/admin/audit-log`) — trilha somente leitura de todas as mutações feitas por platform admins: `actorUserId · action · target · ip · createdAt`. A gravação é centralizada em uma função (`recordAuditLog`), nunca por inserção direta nos roteadores, para que nenhuma rota futura deixe de registrar. O autor é localizado por uma junção do tipo best-effort, e não por chave estrangeira — uma linha sobrevive mesmo se a conta do autor for deletada mais tarde, que é exatamente o registro que um operador precisa ver.
- **Notificações** (`/admin/notifications`) — uma demonstração em tempo real do pipeline de notificações direcionado a um usuário qualquer: escolha uma equipe, escolha um membro, envie uma notificação e veja o sininho atualizar instantaneamente. Consulte [Notificações](/docs/saas-starter-kit/features/notifications#sending-to-another-user-the-admin-demo) para ver o procedimento por trás disso.

## Other known limits

- Sem personificação de locatários pelo proprietário da plataforma.
- Sem lista de permissões (allowlist) de IP para `/admin` até o momento.
- Sem ação self-service para mover uma equipe existente para um plano diferente — apenas criação e mudanças de status.

## Reference: how access is actually checked

Todo procedimento de servidor em `/admin/*` exige todos os três requisitos — você não precisa gerenciar isso manualmente, é útil apenas para depurar um erro `FORBIDDEN`:

1. Uma linha ativa (não revogada) para o usuário na tabela `PlatformAdmin` (do passo 3 acima).
2. MFA cadastrado nessa linha.
3. Uma sessão elevada atualmente válida (um código inserido nos últimos 30 minutos).

A ausência de qualquer um dos três retorna o mesmo erro genérico `FORBIDDEN` — a resposta nunca diz qual deles falhou. Existem duas funções, `SUPER_ADMIN` e `SUPPORT`; hoje ambas passam pela mesma barreira sem diferença no que podem executar.
