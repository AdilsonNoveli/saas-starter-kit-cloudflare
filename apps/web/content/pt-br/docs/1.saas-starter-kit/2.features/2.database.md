O Nuxfire usa o **Postgres** como seu banco de dados principal, acessado a partir dos Cloudflare Workers por meio do [Hyperdrive](https://developers.cloudflare.com/hyperdrive/), com o [Drizzle ORM](https://orm.drizzle.team/).

## Database Architecture

### 1. Schema Definition

As definições de tabelas são divididas entre `apps/functions/src/database/core-schema.ts` e o `server/database/schema.ts` de cada layer, todas usando o dialeto Postgres do Drizzle (`pgTable`, `pgEnum`). `apps/functions/src/database/schema.ts` não é onde as tabelas são definidas — é um agregador manual que reexporta todas elas (`export * from "./core-schema"` mais uma linha por layer) atrás de um único caminho de importação `@nuxfire/functions/schema`:

- **`core-schema.ts`** — Usuários, Tarefas (Jobs), Logs, Registros de Dead Letter, E-mails de Waitlist.
- **`layers/teams/server/database/schema.ts`** — Equipes, Participações em Equipes (Memberships), Convites, Funções (Roles), Permissões.
- **`layers/billing/server/database/schema.ts`** — Planos, Benefícios, Benefícios do Plano, Assinaturas.
- **`layers/notifications/server/database/schema.ts`** — Notificações.
- **`layers/admin/server/database/schema.ts`** — Administradores da Plataforma, Logs de Auditoria.

Desativar um layer de funcionalidade (`layers.features` em `config.ts`) remove suas páginas e componentes do bundle do Nuxt, mas nunca suas tabelas — `schema.ts` inclui o schema de todas as camadas incondicionalmente. As quatro camadas centrais (`teams`, `billing`, `notifications`, `admin`) não são alternáveis. Vários desses arquivos importam dependências cruzadas entre a barreira do agregador e dos layers (por exemplo, `core-schema.ts` importa `teams` de `layers/teams` para a chave estrangeira de `Job`, enquanto `layers/teams` importa `users`/`jobs` de volta de `core-schema.ts`) — sempre por um especificador de pacote (`@nuxfire/layer-teams/...`), nunca por caminho relativo, pois o empacotador de Workers do SST (usado no deploy de `cron.ts`/`jobs-consumer.ts`/`dlq-consumer.ts`) falharia ao resolver caminhos relativos externos ao pacote.

### 2. Infrastructure Setup

Workers não mantêm conexões TCP diretas com o Postgres, portanto o banco de dados é acessado através do Hyperdrive, configurado em `infra/database.ts`:

```typescript [infra/database.ts]
export const database = new sst.cloudflare.Hyperdrive("AppDB", {
  origin: {
    scheme: "postgres",
    host: secret.DatabaseHost.value,
    port: secret.DatabasePort.value.apply(Number),
    database: secret.DatabaseName.value,
    user: secret.DatabaseUser.value,
    password: secret.DatabasePassword.value,
  },
});
```

O Hyperdrive gerencia o pool e o cache da conexão; a aplicação sempre se comunica via protocolo de rede nativo do Postgres, tornando a origem intercambiável — Supabase, RDS, Neon, self-hosted — sem alterar o código do aplicativo.

> **Modo de conexão do Supabase:** A documentação oficial do Hyperdrive na Cloudflare [recomenda explicitamente o uso da conexão Direct do Supabase](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/) em vez de strings de conexão agrupadas (pooler), porque o Hyperdrive já faz o agrupamento de conexões na borda da Cloudflare (evitando duplo pooling). Consulte [Variáveis de Ambiente — Use a conexão Direct](/docs/saas-starter-kit/getting-started/environment-variables#use-the-direct-connection-not-the-session-pooler) para notas sobre formatação de host/usuário e migrações locais em redes IPv6.

### 3. Database Connection

`useDB()` (`apps/app/server/utils/db.ts`) cria um cliente `drizzle-orm/postgres-js` a partir do binding do Hyperdrive, com escopo para a requisição atual e nunca mantido em cache global:

```typescript [apps/app/server/utils/db.ts]
function createDB() {
  const sql = postgres(binding.connectionString, { max: 5, fetch_types: false });
  return drizzle(sql, { schema });
}

export function useDB() {
  const event = useEvent();
  const ctx = event.context as { _db?: DB };
  if (!ctx._db) ctx._db = createDB();
  return ctx._db;
}
```

Isso é fundamental porque um cliente `postgres.js` é um objeto de E/S (I/O), e os Workers encerram o I/O de uma requisição assim que ela termina — reutilizar um cliente construído em uma requisição anterior dentro de uma posterior causa falhas intermitentes (a Cloudflare documenta isso como "Cannot perform I/O on behalf of a different request"). O pooling de conexões do próprio Hyperdrive já elimina o custo de abrir um novo cliente por requisição, portanto não há ganho em armazenar clientes em cache entre requisições, apenas riscos.

## Database Usage

Exemplo de consulta utilizando a API relacional do Drizzle:

```typescript
const team = await useDB().query.teams.findFirst({
  where: or(eq(teams.id, teamIdentifier), eq(teams.slug, teamIdentifier)),
  with: {
    memberships: {
      with: {
        user: { columns: { id: true, name: true, email: true, image: true } },
        role: { columns: { id: true, name: true } },
      },
    },
  },
});
```

## Database Migrations

As migrações são geradas com o Drizzle Kit a partir de `core-schema.ts` e do `server/database/schema.ts` de cada camada — a lista exata declarada em `apps/functions/drizzle.config.ts` sob `schema: [...]` (`dialect: "postgresql"`) — e versionadas em `apps/functions/src/database/migrations/`:

```bash
cd apps/functions
DATABASE_HOST=... DATABASE_PORT=5432 DATABASE_USER=... DATABASE_PASSWORD=... DATABASE_NAME=... \
  bunx drizzle-kit generate
```

Revise o SQL gerado antes de commitar — o Drizzle Kit compara os arquivos de schema acima com o último snapshot em `migrations/meta/`, mas não conhece a intenção de negócio (como renomear uma coluna versus apagar e recriar), portanto confira operações destrutivas com atenção redobrada.

### Deployment

Todo deploy do Worker `App` executa `drizzle-kit migrate` automaticamente, logo após o build do Worker (veja `infra/utils/nuxt.ts`), usando os secrets `DatabaseHost`/`DatabasePort`/`DatabaseUser`/`DatabasePassword`/`DatabaseName`. Não há etapas de migração manuais separadas para rodar em produção.

### Rollback strategy

O Drizzle Kit não gera migrações reversas (down migrations) — as migrações Postgres aqui são do tipo append-only. Em resumo (detalhes completos em `apps/functions/src/database/MIGRATIONS.md`):

- **Mudanças aditivas** (nova tabela, coluna anulável, índice) podem permanecer em produção com segurança mesmo que o deploy do código seja revertido.
- **Mudanças destrutivas** (remover coluna/tabela, novo `NOT NULL`, alterações de tipo) devem ser entregues em migração própria, aplicada somente após o código dependente da estrutura antiga ter rodado com sucesso por um período — o padrão padrão de expandir/contrair (expand/contract).
- Uma migração problemática que chegue à produção é corrigida com uma nova migração para a frente, nunca com reversão manual.
- Faça backups manuais antes de qualquer migração que altere ou remova colunas contendo dados.
