## Supported Payment Providers

- Stripe
- Paddle

Ambos os provedores são configurados para operar em paralelo, permitindo escolher um deles ou usar ambos.

## Core Components

### Database Schema

```typescript [layers/billing/server/database/schema.ts]
export const plans = pgTable("Plan", {
  id: text("id").$default(() => cuid()).primaryKey().notNull(),
  name: text("name").notNull(),
  description: text("description").notNull(),
  tier: text("tier").default("FREE").notNull(),
  price: text("price").notNull(),
  period: text("period").notNull(),
  provider: text("provider"),
  providerPriceId: text("providerPriceId"),
  providerProductId: text("providerProductId"), // the Stripe Product behind providerPriceId — Prices are immutable, so a changed amount creates a new Price under the same Product
  unitAmount: integer("unitAmount"), // minor units (e.g. cents); null for plans not managed by Stripe's catalog
  currency: text("currency"), // lowercase ISO 4217; null alongside unitAmount
  maxSeats: integer("maxSeats"), // null = unlimited
  limits: jsonb("limits"), // open-ended bag for future quotas
  buyerTeamMode: text("buyerTeamMode").notNull().default("NEW_TEAM"), // "NEW_TEAM" or "EXISTING_TEAM"
  buyerTeamId: text("buyerTeamId"), // the team an EXISTING_TEAM plan adds the buyer to
  isArchived: boolean("isArchived").notNull().default(false), // soft delete
  // ...timestamps
});

export const subscriptions = pgTable("Subscription", {
  id: text("id").$default(() => cuid()).primaryKey().notNull(),
  teamId: text("teamId").notNull().references(() => teams.id),
  status: text("status").default("ACTIVE").notNull(),
  provider: text("provider").notNull(),
  providerSubscriptionId: text("providerSubscriptionId").notNull(),
  planId: text("planId").notNull().references(() => plans.id),
  currentPeriodStart: timestamp("currentPeriodStart", { withTimezone: true }),
  currentPeriodEnd: timestamp("currentPeriodEnd", { withTimezone: true }),
  cancelAtPeriodEnd: boolean("cancelAtPeriodEnd").default(false).notNull(),
  providerMetadata: jsonb("providerMetadata"),
  customerEmail: text("customerEmail"),
  lastPaymentDate: timestamp("lastPaymentDate", { withTimezone: true }),
  nextPaymentDate: timestamp("nextPaymentDate", { withTimezone: true }),
  // ...timestamps
});
```

Uma linha de `Plan` pertence a exatamente um provedor (`provider`/`providerPriceId`) — oferecer o mesmo plano tanto no Stripe quanto no Paddle significa duas linhas em `Plan`, uma para cada provedor.

Cada plano também define onde o comprador entra depois de pagar: num time só dele (`NEW_TEAM`, o comprador vira o dono) ou num time que já existe e que você escolhe (`EXISTING_TEAM`). Você define isso no formulário do plano em `/admin/plans`. A configuração fica guardada; o checkout que age sobre ela ainda não faz parte do starter.

### Webhook Handlers

Localizados em `layers/billing/server/api/webhooks/`:

- `stripe.post.ts` — gerencia eventos de assinatura do Stripe
- `paddle.post.ts` — gerencia eventos de assinatura do Paddle

### Client Integration

O composable `usePayments()` (`layers/billing/app/composables/use-payments.ts`) gerencia o checkout no cliente, com formato diferente por provedor:

```typescript
// Paddle — items with a Paddle price id, opens Paddle's own checkout overlay
const paddle = usePayments("PADDLE");
await paddle?.checkout([{ priceId: "pri_123" }], { data: { teamId: team.id } });

// Stripe — returns a hosted Checkout Session URL to redirect to
const stripe = usePayments("STRIPE");
const sessionUrl = await stripe?.checkout("price_123", team.id);
if (sessionUrl) navigateTo(sessionUrl, { external: true });
```

O checkout do Paddle exige que `NUXT_PUBLIC_PADDLE_CLIENT_TOKEN` esteja configurado — ele dispara um erro explicitamente se o valor estiver vazio, em vez de falhar silenciosamente ao abrir.

## Setup Steps

1. Configure os secrets necessários usando a CLI do SST:

   ```bash
   # Stripe
   sst secret set STRIPE_SECRET_KEY sk_test_xxx
   sst secret set STRIPE_WEBHOOK_SECRET_KEY whsec_xxx

   # Paddle
   sst secret set PADDLE_API_KEY xxx
   sst secret set PADDLE_WEBHOOK_SECRET xxx
   sst secret set PADDLE_CLIENT_TOKEN xxx
   ```

2. Crie os planos em `/admin/plans` — consulte [Console de Platform Admin](/docs/saas-starter-kit/features/platform-admin). Esta é uma ação do proprietário da plataforma, não um script de seed: os planos não são hardcoded, portanto os IDs de preço mantêm-se por ambiente (teste vs. produção) sem alterar código.

   **Para planos gerenciados pelo Stripe, nenhum ID de preço é colado manualmente.** O formulário de administração recebe o valor decimal, moeda e período de cobrança; a função `syncStripePlanCatalog()` em `layers/billing/server/utils/stripe-catalog.ts` cria (ou atualiza) o Produto no Stripe e cria um novo Preço via Stripe API sempre que o valor/moeda/período mudar — os Preços são imutáveis no Stripe, então uma mudança sempre gera um novo Preço e arquiva o antigo sob o mesmo Produto. `providerPriceId`/`providerProductId` continuam como campos manuais para planos no Paddle (o catálogo do Paddle não é administrado por aqui) ou para planos Stripe anteriores a essa sincronização.

3. Configure os endpoints de webhook nos painéis de seus provedores:
   - Stripe: `/api/webhooks/stripe`
   - Paddle: `/api/webhooks/paddle`

### The Free plan

Exatamente um plano é criado automaticamente pelo arquivo `apps/functions/src/database/seed/index.ts` a cada deploy (de forma idempotente — ele verifica se já existe uma linha com `tier: "FREE"` primeiro):

```typescript [apps/functions/src/database/seed/data.ts]
export const FREE_PLAN: InsertPlan = {
  name: "Free Tier",
  tier: "FREE",
  // ...
};
```

Todos os planos pagos são intencionalmente omitidos do seed — como os IDs de preço do Stripe/Paddle variam por ambiente, eles são criados através de `/admin/plans` em vez de serem fixados em um script.
