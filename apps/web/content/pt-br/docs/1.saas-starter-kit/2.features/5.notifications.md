## What's Included

- Notificações em tempo real entregues via WebSockets
- Preferência de ativação/desativação por usuário, persistida no `localStorage`
- Contagem de itens não lidos
- Interface de slideover para exibição de notificações

## Architecture

### Backend

A API de notificações é o roteador tRPC em `layers/notifications/server/trpc/notifications.ts`:

- `list` — notificações deste usuário, da mais recente para a mais antiga.
- `create` — insere uma notificação e a publica imediatamente via WebSockets na mesma chamada.
- `updateReadStatus` — marca um lote de IDs de notificação como lido.

```typescript [layers/notifications/server/trpc/notifications.ts]
create: protectedProcedure
  .input(z.object({ title: z.string(), message: z.string() }))
  .mutation(async ({ ctx: { user, sendWebsocketsEvent }, input }) => {
    const [notification] = await useDB().insert(notifications).values({ ...input, userId: user.id }).returning();
    await sendWebsocketsEvent(user.id, { type: "notification", payload: notification });
    return notification;
  }),
```

Consulte [WebSockets](/docs/saas-starter-kit/features/websockets) para saber como o `sendWebsocketsEvent` alcança o navegador.

### Frontend state

`useNotificationsStore` (`layers/notifications/app/composables/use-notifications-store.ts`) é uma store Pinia:

- Mantém notificações indexadas por ID, além de uma contagem dinâmica de não lidas.
- `initializeNotificationSettings()` / `setNotificationsEnabled()` persistem a preferência de ativação no `localStorage`.
- `fetchAllNotifications()`, `markAsRead()`, `createNotification()` encapsulam as chamadas tRPC acima.

### Real-time updates

`layers/notifications/app/plugins/ws-notifications.client.ts` se inscreve no tópico do próprio usuário logado por meio do plugin de WebSocket; eventos recebidos são adicionados à store e toasts os exibem na tela quando a preferência estiver ativa.

## Components

- `NotificationsSlideover.vue` — a interface da lista de notificações, acoplada ao ícone de sino no cabeçalho do painel de equipe.

## Sending to another user: the admin demo

`notifications.create` acima notifica apenas o *próprio usuário solicitante* — não existe um campo `targetUserId`, porque nada decide ainda quem tem permissão de notificar quem (isso requer uma função cross-tenant real, que este starter kit não modela). O que ele entrega como demonstração do mesmo pipeline em tempo real voltado para outro usuário é `/admin/notifications` (consulte [Console de Platform Admin](/docs/saas-starter-kit/features/platform-admin)), uma página exclusiva de platform admin que escolhe uma equipe, seleciona um membro dessa equipe e envia a ele uma notificação em tempo real através de um procedimento dedicado:

```typescript [layers/notifications/server/trpc/admin-notifications.ts]
send: platformAdminProcedure
  .input(z.object({ targetUserId: z.string(), title: z.string(), message: z.string() }))
  .mutation(async ({ ctx: { sendWebsocketsEvent }, input }) => {
    const [notification] = await useDB().insert(notifications)
      .values({ title: input.title, message: input.message, userId: input.targetUserId })
      .returning();
    await sendWebsocketsEvent(input.targetUserId, { type: "notification", payload: notification });
    return notification;
  }),
```

Mesma tabela e mesma chamada `sendWebsocketsEvent` do roteador de tenants — a única diferença é que o `userId` vem do input em vez da sessão do chamador, e o procedimento fica protegido por `platformAdminProcedure` em vez de `protectedProcedure`. Um recurso de "proprietário de equipe notifica seus membros" reutilizaria essa exata estrutura assim que a aplicação tiver uma permissão autorizada a executá-lo.

## Settings

A preferência é exposta em dois lugares, ambos lendo e escrevendo no mesmo estado da store:

- `layers/notifications/app/pages/account-settings/notifications.vue` — a nível de conta.
- `layers/notifications/app/pages/[[team]]/settings/notifications.vue` — a nível de equipe.
