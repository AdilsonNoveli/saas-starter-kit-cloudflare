O [SST](https://sst.dev) é a camada de infraestrutura como código sobre a qual o Nuxfire é construído. Cada recurso da Cloudflare — Workers, Hyperdrive, KV, R2, D1, Queues, Durable Objects, Cron, DNS — é um recurso `sst.cloudflare.*` (ou `sst.*` puro) declarado em TypeScript sob a pasta `infra/`, sem arquivos `wrangler.toml`/`wrangler.json` feitos à mão e sem execuções de `wrangler deploy` por fora do SST.

## How the pieces load

O arquivo `sst.config.ts` é o ponto de entrada. Seu método `run()` não lista recursos diretamente — ele lê todos os arquivos `.ts` em `infra/` e os importa, mesclando o `outputs` exportado por cada um nos outputs finais da stack:

```typescript [sst.config.ts]
async run() {
  const outputs = {};
  for (const value of readdirSync("./infra/").filter((x) => x.endsWith(".ts"))) {
    const result = await import("./infra/" + value);
    if (result.outputs) Object.assign(outputs, result.outputs);
  }
  return outputs;
},
```

Assim, `infra/database.ts`, `infra/auth.ts`, `infra/app.ts`, `infra/jobs.ts`, `infra/websockets.ts`, `infra/cron.ts`, `infra/web.ts`, `infra/emails.ts`, `infra/dns.ts` e `infra/secret.ts` são apenas módulos que declaram seus próprios recursos — não existe um arquivo de "stack" central monolítico para manter sincronizado.

A instrução `home: "cloudflare"` na mesma configuração significa que o próprio estado do SST (recursos implantados, identificadores) é armazenado na sua conta da Cloudflare, e não na AWS — dispensando qualquer conta da AWS nesta arquitetura.

## Stages

Um **estágio** (stage) é um ambiente isolado e nomeado — com seus próprios Workers, sua própria conexão com o banco de dados e seus próprios secrets. O arquivo `infra/dns.ts` transforma o nome do estágio em um domínio real:

```typescript [infra/dns.ts]
export const domain =
  { production: prodDomain }[$app.stage] || `${$app.stage}.${devDomain}`;
```

O estágio chamado `production` aponta para `prodDomain` de `config.ts`; qualquer outro nome de estágio aponta para `<stage>.<devDomain>` — e é por isso que `bun run deploy` sem flags, executado por um desenvolvedor chamado `alex`, publica em `alex.dev.seudominio.com`.

O `sst.config.ts` também trata o estágio `production` de forma diferenciada propositalmente:

```typescript [sst.config.ts]
removal: input?.stage === "production" ? "retain" : "remove",
protect: ["production"].includes(input?.stage),
```

Recursos de qualquer outro estágio são destruídos ao rodar `sst remove`; os de `production` são retidos e protegidos contra remoção acidental.

## Secrets

Cada `sst.Secret` declarado pelo Nuxfire fica em `infra/secret.ts`, com escopo **por estágio** — carregar um valor no seu estágio dev local nunca altera o cofre de `production`, e vice-versa. Consulte [Secrets](/docs/saas-starter-kit/getting-started/secrets) para ver o fluxo de `sst secret load`, e atente-se à exceção: `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` nunca são `sst.Secret`s — o SST precisa deles como variáveis reais de ambiente no terminal antes de poder autenticar e abrir o cofre.

## Deploying

```bash
bun run deploy                          # your personal dev stage
bun run deploy -- --stage production    # production
bun run deploy -- --stage custom-name   # any other named stage
```

`bun run deploy` (`scripts/deploy.ts`) roda a verificação prévia (`scripts/doctor.ts`, também disponível sozinha como `bun run doctor`) e depois o `sst deploy`, repassando os mesmos argumentos aos dois; o separador `--` é obrigatório para que a flag `--stage` chegue até eles em vez de ser interceptada pelo `bun run`. Chamar `sst deploy` diretamente também funciona, mas pula a verificação prévia.
