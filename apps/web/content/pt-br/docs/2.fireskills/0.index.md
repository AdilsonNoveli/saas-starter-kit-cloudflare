O **Fireskills** é o método orientado a especificações que já vem dentro do Nuxfire. Você descreve o que quer no chat do agente da sua IDE; o agente segue um fluxo fixo (capturar, refinar, especificar, provar, implementar, documentar) e trabalha com um conjunto de especialistas técnicos que já conhecem este código.

Em vez de prompts soltos, toda mudança passa por um único arquivo normativo, gates de qualidade e evidência. Quando o código e a documentação divergem, **o código vence**.

**Novo por aqui? Comece pelo [Início Rápido](/docs/fireskills/getting-started/quick-start):** ele lista o que digitar na IDE para cada coisa que você pode querer fazer.

## Pilares

### 1. Uma especificação normativa por fatia

Toda feature, correção ou mudança vive em exatamente um arquivo: `specs/<state>/<NNNN>-<slug>/spec.md`. Requisitos, cenários Gherkin, tarefas, checklists, evidência de testes e gates ficam todos nele. Não existem `plan.md`, `tasks.md` nem `research.md`.

### 2. Três atos, três gates

- O **Ato I, Definir** (Inbox, Backlog, Specify, Validate) termina no **Definition Gate**.
- O **Ato II, Projetar e Provar** (Tasks, TDD/BDD) termina no **Plan Gate**: as tarefas existem e os testes falham pelo motivo certo (RED).
- O **Ato III, Entregar** (Implement, Documentator) termina no **Delivery Gate**: testes verdes, tipos verificados, evidência registrada, documentos de contexto atualizados.

### 3. 34 especialistas técnicos

Carregados pelo agente antes de tocar em código na área deles:

- **11 especialistas da stack do Nuxfire**: Nuxt 4, `@nuxt/ui` v4, layers do Nuxfire, tRPC v10, Drizzle, `nuxt-authorization`, OpenAuth.js, Pinia, Billing (Stripe e Paddle), Cloudflare Workers, SST 4. Cada um tem um `references/nuxfire-*.md` com o que existe no código e o que **não** existe.
- **23 especialistas de engenharia**: TypeScript, PostgreSQL, Tailwind, arquitetura, design de APIs, segurança, performance, observabilidade, depuração, code review, acessibilidade, UX/UI, versionamento, git e mais.

### 4. Uma CLI pequena para as partes mecânicas

`bun run fireskill` (código em `fireskills/cli/`, Bun e TypeScript) move specs entre estados, define a nota de esforço, valida uma spec com um linter rápido, mostra o progresso, sincroniza milestones e gerencia lições aprendidas. Veja a [referência da CLI](/docs/fireskills/cli/commands).

### 5. Contexto persistente em `.specsfy/`

`PROJECT.md`, `STACK.md`, `RULES.md`, `DATABASE.md`, `INTERFACE.md`, `DESIGNSYSTEM.MD`, `PACKAGES.md`, `USER-PROFILE.md` e `LESSONS.md`/`lessons.json`. Os agentes os leem antes de perguntar qualquer coisa a você. Veja [Contexto do Projeto](/docs/fireskills/getting-started/project-context).

### 6. Segurança em torno do banco de dados e de ações irreversíveis

O código de servidor roda em Cloudflare Workers via SST. O fluxo nunca faz deploy, apaga dados ou executa um comando destrutivo no banco por conta própria; um script de proteção classifica os comandos (`drizzle-kit push --force`, `db:wipe`, `DROP`, `TRUNCATE` e outros são recusados mesmo com a sua aprovação), e testes que chegam ao PostgreSQL exigem um banco de teste separado.
