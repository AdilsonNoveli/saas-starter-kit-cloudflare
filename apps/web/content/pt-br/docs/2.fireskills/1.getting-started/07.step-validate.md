**Skill:** `fireskill-04-validate` · **Faz perguntas:** só se precisar voltar ao backlog · **Altera:** o cabeçalho e a seção 13 do `spec.md`; move a spec para `specs/defined/`

## Quando usar

A spec está escrita e você quer saber se ela está pronta para ser planejada. O fluxo chega a esta etapa sozinho depois da Etapa 3.

## O que digitar

```text
Use $fireskill-04-validate para auditar specs/<estado>/<NNNN>-<slug>/spec.md, seu research/ e os gates antes das tarefas. Orquestre transições automáticas com anúncio, execução e retomada na mesma conversa.
```

Troque o caminho, por exemplo `specs/draft/0001-convite-de-membros-por-e-mail/spec.md`.

## O que o agente faz

1. Confirma o formato (`Formato: Specsfy/2.0`), os três atos em ordem, o slug igual ao diretório, e que o pacote tem só o `spec.md` e um `research/` opcional.
2. Roda o validador estrutural da skill:

   ```bash
   node fireskills/skills/fireskill-04-validate/scripts/validate_spec.mjs specs/draft/<NNNN>-<slug>/spec.md --allow-draft
   ```

3. Faz uma **revisão semântica**: compara research, requisitos, BDD, plano técnico, modelo de dados, contratos, TDD, matriz e tarefas. Confirma pelo menos três `AC` distintos para a feature e para cada `US`, `FR` e `NFR`. Para uma tela, exige que a seção 10 esteja completa; um CRUD sem telas e formulários é um `BLOCKER`.
4. Se a definição muda a stack ou a persistência, exige que a Definition of Done cite `.fireskills/STACK.md` ou `.fireskills/DATABASE.md`.
5. Devolve exatamente um resultado:

   | Resultado | Significado | O que acontece |
   |---|---|---|
   | `READY` | nenhuma falha estrutural e nenhum `BLOCKER` sem resolução | `Definition Gate: Passed`, `Status: Defined`, depois `bun run fireskill transition <id> defined`, depois passa a vez para o `$fireskill-05-tasks` |
   | `NOT READY` | uma falha estrutural ou um `BLOCKER` | `Definition Gate: Failed`, `Status: Draft`; volta para o `$fireskill-02-backlog` se falta uma decisão, ou para o `$fireskill-03-specify`/`$fireskill-update-spec` se a correção já está decidida |

A mesma skill também fecha a entrega no fim do fluxo: em `specs/review/`, com o Delivery Gate passado, ela move a spec para `completed`. Veja a [Etapa 7](/docs/fireskills/getting-started/step-implement).

## Dois validadores, dois trabalhos

| Comando | O que é | O que verifica |
|---|---|---|
| `validate_spec.mjs` (a skill) | **O gate.** Usado pelo `$fireskill-04-validate`. | Formato, atos e seções, IDs, cobertura de pelo menos três `AC` por requisito, contrato de interface, índice de research |
| `bun run fireskill validate <id> [--strict]` (a CLI) | **Um linter rápido** que você mesmo pode rodar. | `Effort` entre 1 e 10, `Effort rationale`, `Status`; cinco seções encontradas pelo título (contexto/problema, atores/requisitos/escopo, cenários BDD, tarefas, testes/evidência); um cenário BDD; uma lista de tarefas. Placeholders como `[TODO]` são avisos; `--strict` transforma avisos em erros. |

O linter da CLI **não** conta `AC`, não verifica o contrato de interface, não altera os gates e não move a spec. Passar nele não é o Definition Gate.

```bash
bun run fireskill validate 0001 --strict
```

```text
Status: VALID (Passed spec linter)
Errors: 0 | Warnings: 0
```

## O `transition` não verifica gates

O `bun run fireskill transition <id> <folder>` move a spec um passo (`draft` ↔ `defined` ↔ `planned` ↔ `in-progress` ↔ `review` ↔ `completed`) e atualiza o `Status`. Ele **não** lê os gates: um salto como `defined` → `in-progress` é recusado (`invalid transition`), mas nada impede você de mover uma spec cujo gate está `Pending`. Deixe as skills fazerem as movimentações; elas só as fazem depois que o gate delas passou.

## Opcional: ataque a spec primeiro

Para uma spec de alto esforço ou arriscada (Effort 7 ou mais), peça uma revisão adversarial antes de aprovar. Veja o `$fireskill-the-fool` em [Outros pontos de entrada](/docs/fireskills/getting-started/other-entry-points).
