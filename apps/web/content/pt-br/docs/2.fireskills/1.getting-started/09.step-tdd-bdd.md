**Skill:** `fireskill-06-tdd-bdd` · **Faz perguntas:** não · **Cria:** arquivos de teste Vitest ao lado do código; atualiza a tabela de evidência do `spec.md`

## Quando usar

Normalmente você não a chama: o `$fireskill-05-tasks` a chama no modo `prepare`. Chame você mesmo quando quiser mais um teste que falha, um `cycle` ou uma auditoria.

## O que digitar

```text
Use $fireskill-06-tdd-bdd para ler o Gherkin de referência em specs/<estado>/<NNNN>-<slug>/spec.md, criar testes TDD rastreáveis e executar RED-GREEN-REFACTOR sem executar .feature. Orquestre transições automáticas com anúncio, execução e retomada na mesma conversa.
```

Você pode indicar o modo na mesma mensagem: `prepare`, `cycle` ou `verify`.

## Os três modos

| Modo | Quando | O que faz |
|---|---|---|
| `prepare` | antes da implementação (spec `Defined`, `Plan Gate: Pending`) | escreve o próximo teste e prova o RED, **sem** código de produção; marca como concluída só essa tarefa `[TEST]`; volta para o `$fireskill-05-tasks` |
| `cycle` | durante a implementação (spec `Planned` ou `Implementing`) | RED → GREEN → REFACTOR para uma fatia escolhida |
| `verify` | a qualquer momento | roda as suítes e audita a rastreabilidade, sem criar comportamento novo |

Se você não disser, ela usa `prepare` quando a lista de tarefas ainda não está sendo executada e `cycle` quando há uma tarefa ativa.

## Como um teste é escrito

- O bloco Gherkin do `AC` no `spec.md` é a referência. **Nenhum arquivo `.feature` é criado nem executado.**
- Os testes são Vitest, ao lado do código na sua layer (`shared/**/*.test.ts` ou `server/**/*.test.ts`), no menor nível que prova o comportamento. Exemplos reais: `layers/teams/shared/utils/abilities.test.ts`, `layers/teams/server/utils/team-seats.test.ts`.
- Cada caso executável carrega o seu próprio marcador, logo ao lado da sua definição:

  ```ts
  // SPECSFY: US-001 FR-001 AC-001
  it("rejeita convite de quem não é administrador", async () => {
    // …
  });
  ```

- Pelo menos **três casos distintos** para a feature inteira e para cada `US`, `FR` e `NFR`: caminho feliz, regra ou variação crítica, falha ou limite relevante. Um marcador compartilhado por um arquivo inteiro conta como um caso.
- Todo `AC` é coberto por pelo menos um caso.

## RED, GREEN, REFACTOR

1. **RED**: escreva o menor teste que prova o `AC`, rode-o (`bun run test`, ou `bunx vitest run <file>`) e confirme que ele falha **porque o comportamento não existe**. Uma falha por sintaxe, import, fixture ou ambiente não conta. Um teste que passa antes da mudança não prova nada e precisa ser refinado.
2. **GREEN** (no `cycle`): o mínimo de código de produção, primeiro o teste focal, depois a suíte relacionada.
3. **REFACTOR**: limpe o código com os testes verdes.

Cada passo é registrado na tabela `Evidência RED-GREEN-REFACTOR` da spec.

## Proteção do banco de dados

Antes de qualquer teste rodar, o `check_database_safety.mjs` classifica o comando. Se não for `SAFE`, nenhum teste roda e a etapa fica pendente. Testes que chegam ao PostgreSQL precisam de um banco de teste dedicado; use uma transação revertida ou fixtures limitadas ao caso.

## Confira a rastreabilidade você mesmo

```bash
node fireskills/skills/fireskill-06-tdd-bdd/scripts/check_traceability.mjs specs/planned/<NNNN>-<slug>/spec.md .
bun run test
```
