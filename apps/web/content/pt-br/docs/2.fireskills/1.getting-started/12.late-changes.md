**Skill:** `fireskill-update-spec` · **Faz perguntas:** só quando as opções mudam o resultado de forma material · **Altera:** o `spec.md` e apenas os gates que a mudança invalida

## Quando usar

Uma spec já passou o Definition Gate (está `Defined`, `Planned`, `Implementing`, `Reviewing` ou `Complete`) e você quer acrescentar, remover, corrigir ou mudar algo. Para uma spec ainda em `Draft` que nunca passou o gate, use a [Etapa 3: Specify](/docs/fireskills/getting-started/step-specify).

## O que digitar

```text
Use $fireskill-update-spec para incorporar este novo pedido à especificação existente e orquestrar transições automáticas até a retomada.

specs/planned/0001-convite-de-membros-por-e-mail/spec.md
O link do convite agora expira em 24 horas, não em 48.
```

## O que o agente faz

1. Guarda o seu pedido palavra por palavra antes de interpretá-lo, depois localiza a spec e lê o cabeçalho, os requisitos, os cenários, o plano, as tarefas, os gates e a evidência. Mudanças já existentes no Git na spec não são atribuídas ao seu pedido.
2. **Classifica** a mudança antes de escrever:

   | Mudança | O que faz |
   |---|---|
   | interna, reversível, sem efeito observável | não toca na spec; registra a avaliação na evidência da tarefa e retoma a implementação |
   | editorial, mesmo sentido | edita só a redação; mantém status e gates |
   | comportamento, aceite, escopo, dados, segurança ou interface | reabre a partir do **Ato I**: `Status: Draft`, os três gates `Pending` |
   | só solução, tarefas ou estratégia de testes | reabre a partir do **Ato II**: `Status: Defined`, o `Definition Gate` continua `Passed`, `Plan Gate` e `Delivery Gate` voltam a `Pending` |
   | uma capacidade nova e independente | não a acrescenta em silêncio: vai para o `$fireskill-02-backlog` ou o `$fireskill-03-specify` |

3. Edita só o `spec.md` (e o `research/` indexado). Mantém os IDs existentes e nunca renumera. Para uma mudança de comportamento, registra motivo, decisão e IDs impactados na seção 17. Nunca cria `change-request.md` nem qualquer arquivo paralelo.
4. Projeta o impacto (somente leitura):

   ```bash
   node fireskills/skills/fireskill-update-spec/scripts/analyze_change.mjs specs/<state>/<NNNN>-<slug>/spec.md --base HEAD --mode impact
   ```

   `--mode changelog` lista os IDs adicionados, removidos e alterados.
5. Roda a validação estrutural (`validate_spec.mjs … --allow-draft`) e **retoma** o fluxo:
   - mudança a partir do Ato I: `$fireskill-04-validate`, depois tarefas, TDD/BDD e a etapa que levantou a mudança;
   - mudança só no Ato II: `$fireskill-05-tasks`, que reconcilia o plano, chama o `$fireskill-06-tdd-bdd` e retoma;
   - mudança encontrada durante a implementação: o `$fireskill-07-implement` retoma só quando os Definition e Plan Gates voltam a `Passed` e existe um RED válido para o comportamento novo;
   - mudança depois de `Complete`: os atos invalidados rodam de novo e o `Complete` só volta com o Delivery Gate e a Definition of Done comprovados; a spec volta primeiro para `review`.

A evidência histórica nunca é reescrita como se tivesse sido produzida para o novo pedido: a prova que depende da versão invalidada é marcada como pendente.

## As movimentações de pasta

O `bun run fireskill transition` permite voltar um passo (`completed` → `review`, `review` → `in-progress`, `in-progress` → `planned`, `planned` → `defined`, `defined` → `draft`), nunca por salto. A skill o usa conforme necessário.
