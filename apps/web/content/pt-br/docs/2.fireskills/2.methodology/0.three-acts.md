A metodologia do Fireskills organiza todo o trabalho de engenharia em **Três Atos**. Cada Ato representa uma mentalidade, um conjunto de ferramentas e um limiar de validação distintos, garantindo que a implementação nunca comece sem requisitos claros e contratos de teste comprovados.

```text
┌──────────────────────────────────────┐
│            ACT I: DEFINE             │
│ • User Stories (US)                  │
│ • Requirements (FR/NFR)              │
│ • Gherkin BDD Scenarios              │
│ ──> Definition Gate: Passed          │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│        ACT II: DESIGN & PROVE        │
│ • Task Decomposition & 6-Step List   │
│ • Executable TDD Tests               │
│ • Observed RED State                 │
│ ──> Plan Gate: Passed                │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│           ACT III: DELIVER           │
│ • RED -> GREEN Implementation        │
│ • Visual Inspection against Tokens   │
│ • Full Regression & Documentator     │
│ ──> Delivery Gate: Passed            │
└──────────────────────────────────────┘
```

---

## Ato I: Definir

**Objetivo**: Estabelecer o que precisa ser construído, por que importa, a quem serve e quais critérios definem o sucesso.

### Atividades:
- **Recepção e esclarecimento de escopo**: Trazer os pedidos brutos de `specs/inbox/` para `specs/backlog/`.
- **Descoberta com as partes interessadas**: Conduzir uma investigação estruturada pelo Contrato de Perguntas Numeradas para resolver ambiguidades e casos-limite.
- **Redação da especificação**: Documentar Histórias de Usuário (`US`), Requisitos Funcionais (`FR`) e Requisitos Não Funcionais (`NFR`).
- **Cenários BDD em Gherkin**: Formular especificações de comportamento legíveis por humanos (`Given / When / Then`) diretamente no `spec.md`.
- **Descoberta de UI e dados**: Especificar as telas afetadas, entradas, estados de erro e modificações de schema.

### Limiar de saída:
O Ato I só termina quando o **Definition Gate** é formalmente marcado como `Passed`.

---

## Ato II: Projetar e Provar

**Objetivo**: Formular o plano técnico e provar que o nosso entendimento está correto, estabelecendo testes que falham (RED) antes de escrever qualquer código de aplicação.

### Atividades:
- **Decomposição em tarefas**: Dividir a spec em tarefas atômicas e sequenciadas dentro do `spec.md`. Cada tarefa deve seguir o checklist obrigatório de 6 itens (`PREP`, `EXECUTE`, `VERIFY`, `VISUAL`, `EVIDENCE`, `IMPROVE`).
- **Alinhamento arquitetural**: Selecionar os padrões técnicos adequados, garantindo compatibilidade com as restrições do Cloudflare Workers.
- **Derivação de testes TDD**: Derivar suítes de teste Vitest executáveis diretamente dos cenários Gherkin de referência. Todo caso executável carrega o seu próprio marcador `// SPECSFY:`.
- **Observação de um RED válido**: Rodar a suíte de testes (`bun run test`) e observar que os testes falham estritamente porque a funcionalidade ainda não foi implementada, e não por erros de sintaxe ou de ambiente.

### Limiar de saída:
O Ato II só termina quando o **Plan Gate** é formalmente marcado como `Passed`.

---

## Ato III: Entregar

**Objetivo**: Implementar código de nível de produção, fazer os testes passarem (GREEN), conduzir revisões visuais e empacotar a prova verificada.

### Atividades:
- **RED → GREEN → REFACTOR**: Escrever código mínimo e limpo para deixar os testes que falham verdes. Refatorar por clareza, desempenho e aderência aos padrões da stack.
- **Verificação de design visual**: Inspecionar as interfaces renderizadas em viewports de desktop e mobile contra o `.specsfy/DESIGNSYSTEM.MD`, verificando tipografia, espaçamento, padding, bordas e acessibilidade.
- **Suíte de regressão**: Executar as suítes de teste completas e os verificadores de tipos (testes a partir da raiz; tipos a partir de `apps/app`):
  ```bash
  bun run test                       # repository root
  cd apps/app
  bun run typecheck
  bunx vue-tsc --noEmit -p server/tsconfig.json
  ```
- **Sincronização de contexto e documentação**: Atualizar os arquivos de contexto do `.specsfy` (`DATABASE.md`, `INTERFACE.md`) e rodar o `fireskill-documentator`.

### Limiar de saída:
O Ato III só termina quando o **Delivery Gate** é formalmente marcado como `Passed` e a especificação é transicionada para `completed`.

---

## Reabrindo Atos por Mudança de Requisitos

Se os requisitos mudam no meio do ciclo, os gates seguintes não podem continuar válidos:
- **Mudança de requisito ou de comportamento**: Reabre os Atos I, II e III. O Definition Gate e o Plan Gate voltam a `Pending`.
- **Mudança no plano técnico**: Reabre os Atos II e III. O Definition Gate continua `Passed`, enquanto o Plan Gate volta a `Pending`.
