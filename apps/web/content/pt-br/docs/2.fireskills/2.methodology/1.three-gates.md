Os gates de qualidade são registrados no cabeçalho da spec, nos campos `Definition Gate`, `Plan Gate` e `Delivery Gate`. Uma skill só define um gate com a evidência que esse gate exige; um gate posterior nunca continua aprovado em cima de um gate anterior invalidado.

```markdown
| Campo | Valor |
| --- | --- |
| Status | Implementing |
| Definition Gate | Passed |
| Plan Gate | Passed |
| Delivery Gate | In Progress |
```

Valores vistos no fluxo: `Pending` (não avaliado), `Passed`, `Failed` (a última verificação não passou) e, para o Delivery Gate enquanto o trabalho está em andamento, `In Progress`.

---

## 1. Definition Gate (encerra o Ato I)

Responsável: `$fireskill-04-validate`. O resultado `READY` define `Definition Gate: Passed` e `Status: Defined`; `NOT READY` define `Failed` e mantém `Draft`.

O que ele exige:

1. **Formato**: `Formato: Specsfy/2.0`, os três atos em ordem, slug igual ao diretório, pacote só com `spec.md` e `research/` opcional.
2. **Cobertura**: pelo menos **três `AC` distintos** para a feature inteira e para cada `US`, `FR` e `NFR`, contados somente quando o `AC` declara o ID em `**Cobre**`.
3. **Cenários**: Gherkin Given/When/Then na spec, associados aos requisitos.
4. **Interface** (quando `Interface para pessoas: Sim`): seção 10 com stack, telas, fluxo de informação, menus, formulários e ações, composição, componentes, estados e acessibilidade. Um CRUD deve declarar `PageHeader`, `UTable`, a coluna `ID`, editar e apagar.
5. **Dados e contexto**: uma mudança de stack ou de persistência deve constar na Definition of Done para `.fireskills/STACK.md` ou `.fireskills/DATABASE.md`.
6. **Validador estrutural**: `node fireskills/skills/fireskill-04-validate/scripts/validate_spec.mjs specs/<state>/<NNNN>-<slug>/spec.md` (com `--allow-draft` enquanto ainda `Draft`).

O `bun run fireskill validate` é um linter rápido que você também pode rodar, mas não é este gate. Veja a [Etapa 4](/docs/fireskills/getting-started/step-validate).

## 2. Plan Gate (encerra o Ato II)

Responsáveis: `$fireskill-05-tasks` e `$fireskill-06-tdd-bdd`. `Plan Gate: Passed` define `Status: Planned`.

1. Tarefas atômicas na seção 14 com o checklist de seis itens (`PREP`, `EXECUTE`, `VERIFY`, `VISUAL`, `EVIDENCE`, `IMPROVE`).
2. Uma tarefa `[TEST] [TDD]` por `AC`; toda tarefa `[CODE]` depende do seu predecessor TDD.
3. Casos Vitest executáveis, cada um com o seu próprio marcador `// SPECSFY:`, pelo menos três por feature/`US`/`FR`/`NFR`.
4. Um **RED válido** observado: os testes falham porque o comportamento não existe, não por sintaxe ou ambiente.
5. Uma tarefa `[CODE] [MIGRATION]` para toda mudança de schema.
6. `validate_tasks.mjs` (e `validate_interface_tasks.mjs` para telas) passam sem `--allow-draft`.

## 3. Delivery Gate (encerra o Ato III)

Responsável: `$fireskill-07-implement`, com o aceite final pelo `$fireskill-04-validate`. `Delivery Gate: Passed` define `Status: Reviewing`; o aceite então move a spec para `completed` com `Status: Complete`.

1. Todas as tarefas da seção 14 marcadas, com evidência para cada uma.
2. Suíte inteira verde: `bun run test` (raiz do repositório).
3. Tipos limpos: em `apps/app`, `bun run typecheck` e `bunx vue-tsc --noEmit -p server/tsconfig.json`.
4. Rastreabilidade: todo `AC`, `FR`, `NFR` e item da Definition of Done tem evidência atual; sem tarefas abertas, placeholders ou testes pulados.
5. `VISUAL` feito em toda tarefa com tela.
6. Monitor de contexto sem `PENDING`, e `build_documentation.mjs --check` passando.
7. Para cada `[MIGRATION]`: o arquivo, o comando que a aplicou no banco de **teste** e a consulta de estado.
8. Para mudanças em `apps/functions` ou `layers`, um `sst deploy` real é a verificação que importa. Ele precisa da sua autorização explícita; o fluxo não o executa por conta própria.

---

## Invalidação

- Uma mudança de requisitos, cenários, escopo, dados, segurança ou interface manda a spec de volta para `Draft`: os três gates voltam a `Pending`.
- Uma mudança só de tarefas, solução ou estratégia de testes manda de volta para `Defined`: o `Definition Gate` continua `Passed`; `Plan Gate` e `Delivery Gate` voltam a `Pending`.

Essas movimentações são feitas pelo `$fireskill-update-spec`. Veja [Mudanças tardias](/docs/fireskills/getting-started/late-changes).
