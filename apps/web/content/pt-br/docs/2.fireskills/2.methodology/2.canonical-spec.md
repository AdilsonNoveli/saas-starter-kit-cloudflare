`specs/<state>/<NNNN>-<slug>/spec.md` é a única fonte normativa de uma fatia de trabalho. Os arquivos paralelos `plan.md`, `tasks.md`, `research.md` e `data-model.md` não são usados. O arquivo é criado a partir do template `fireskills/skills/templates/Spec.md` pelo `iniciar_spec.mjs`; você não o escreve do zero.

---

## Estrutura de diretórios

```text
specs/
├── inbox/
│   └── 2026-09-18-174245-convite-de-membros-por-e-mail.md
├── backlog/
│   └── 0001-convite-de-membros-por-e-mail.md
├── milestones/            (only when an MVP is imported)
├── draft/
├── defined/
├── planned/
├── in-progress/
├── review/
└── completed/
    └── 0001-convite-de-membros-por-e-mail/
        ├── spec.md
        └── research/      (optional)
```

- `inbox/` e `backlog/` guardam notas e briefs; não são normativos.
- Uma spec existe em exatamente uma pasta de estado; a pasta é o estado operacional.
- `research/` guarda apenas evidência que foi de fato consultada (cópias, snapshots, contratos, exemplos) e é indexada dentro do `spec.md`. Não guarda código de produção nem testes.
- Nada mais é permitido no pacote da spec.

## O cabeçalho

Uma tabela Markdown de duas colunas, `Campo` / `Valor` (não a converta em linhas `**Campo**: valor`). Saída real do `iniciar_spec.mjs`:

```markdown
# Especificação integrada: Convite de membros por e-mail

| Campo | Valor |
| --- | --- |
| Formato | Specsfy/2.0 |
| ID | SPEC-0001 |
| Slug | 0001-convite-de-membros-por-e-mail |
| Status | Draft |
| Effort | 1 |
| Effort updated at | 2026-09-18 |
| Effort rationale | Estimativa inicial; revisar durante a descoberta. |
| ClickUp Task | |
| Milestones | |
| Definition Gate | Pending |
| Plan Gate | Pending |
| Delivery Gate | Pending |
| Evidence Contract | 1 |
| Interface para pessoas | A definir |
| Atualizada em | 2026-09-18 |
```

O `Status` acompanha a pasta: `Draft`, `Defined`, `Planned`, `Implementing`, `Reviewing`, `Complete`. `Interface para pessoas` é `Sim` ou `Não`; `Sim` torna a seção 10 obrigatória.

## Os três atos e as 18 seções

| Ato | Seções |
|---|---|
| **Ato I — Definir** | 1 Problema e resultado · 2 Research e esclarecimentos · 3 Escopo e atores · 4 Princípios e restrições do projeto · 5 Histórias de usuário · 6 Cenários BDD de aceite · 7 Requisitos |
| **Ato II — Projetar e provar** | 8 Plano técnico · 9 Modelo de dados · 10 Interfaces e contratos · 11 Estratégia TDD · 12 Plano de testes e rastreabilidade · 13 Validações · 14 Tarefas · 15 Ordem de execução |
| **Ato III — Entregar e validar** | 16 Dependências, riscos e suposições · 17 Decisões · 18 Definition of Done |

Os IDs têm três dígitos e nunca são renumerados: `US-001`, `FR-001`, `NFR-001`, `AC-001`, `DEC-001`, tarefas `T001`.

### Cenários (seção 6)

Cada `AC` é um título, uma linha `**Cobre**` com os IDs que ele cobre e um bloco Gherkin:

````markdown
#### AC-001 — [comportamento]

**Cobre**: US-001, FR-001, NFR-001

```gherkin
@US-001 @FR-001 @NFR-001 @AC-001
Feature: [capacidade observável]

  Scenario: [caminho feliz aceito]
    Given [estado inicial]
    When [ação]
    Then [resultado observável]
```
````

O Gherkin vive só aqui. Nenhum arquivo `.feature` é criado nem executado.

### Interface (seção 10)

Quando há uma tela: stack e convenções, telas e responsabilidades, fluxo de informação e navegação, menus, formulários e ações, composição, os componentes Vue e `@nuxt/ui` escolhidos, estados e acessibilidade, o contrato de CRUD (`PageHeader`, `UTable` com `enterpriseTableUi`, `ID` visível, link na linha, editar e apagar) e a revisão visual.

### Tarefas (seção 14)

```markdown
- [ ] T001 [TEST] [TDD] [US-001] Derivar teste Vitest do BDD em layers/teams/shared/utils/abilities.test.ts — Refs: FR-002, AC-003 — Depends: none
  - [ ] **PREP**: …
  - [ ] **EXECUTE**: …
  - [ ] **VERIFY**: …
  - [ ] **VISUAL**: …
  - [ ] **EVIDENCE**: …
  - [ ] **IMPROVE**: …
```

Uma mudança no banco de dados inclui uma tarefa `[CODE] [MIGRATION]` apontando para um arquivo versionado em `apps/functions/src/database/migrations/`.

### Testes e rastreabilidade (seções 11–12)

Cada caso Vitest executável carrega o seu próprio marcador ao lado da sua definição:

```ts
// SPECSFY: US-001 FR-001 AC-001
```

O marcador é um comentário; não faz parte do título do teste. A tabela `Evidência RED-GREEN-REFACTOR` registra cada RED e GREEN observado.

---

## Antipadrões

- Criar `plan.md`, `tasks.md`, `todo.md` ou qualquer outro arquivo paralelo.
- Testes sem marcador `// SPECSFY:`, ou um marcador compartilhado por um arquivo inteiro (conta como um caso).
- Uma tarefa sem os seis itens do checklist, ou sem o `VISUAL`.
- Deixar exemplos do template, `TBD` ou `TODO` numa spec marcada como `Defined`.
