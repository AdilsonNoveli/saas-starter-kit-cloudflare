This guide gets a NuxFire stage running end to end: local development, then a real deploy to your Cloudflare account.

## Prerequisites

Before you begin, you'll need:

- A Cloudflare account on a **paid plan** — Workers Paid is required for websockets and queues. Activate it from the "Get started with R2" screen (a credit card is required even though R2 itself has a generous free tier):

  ![Get started with R2](/images/docs/Get-started-with-R2.webp)

- A domain configured with Cloudflare nameservers.
- A Cloudflare API token and Account ID (see [step 2](#2-configure-cloudflare-access) below).
- Your account's `workers.dev` subdomain already provisioned — open **Workers & Pages** in the Cloudflare dashboard once (it's created automatically the first time that section loads). Skip this on a brand-new account and the first deploy fails partway through with `403: "You need a workers.dev subdomain..."` (error code 10063) — the token and account ID are correct, this is a one-time account setup step that has nothing to do with either of them.
- A real Postgres database — Supabase, RDS, Neon, self-hosted, or any standard Postgres. The connection is always over the native Postgres protocol, never a provider-specific SDK.
- GitHub access to the [`pedped-app/nuxfire`](https://github.com/pedped-app/nuxfire) repository.

## Repository Structure

NuxFire is a monorepo with several packages:

- `packages/app`: the main application (dashboard, Nuxt)
- `packages/web`: the public site — landing page, blog, docs
- `packages/auth-frontend`: login/signup UI
- `packages/functions`: Cloudflare Workers code (auth issuer, email, websockets, jobs, cron)
- `packages/emails`: email templates (React Email)

The entire infrastructure — Workers, Hyperdrive, KV, R2, Queues, Durable Objects — is defined as code in `infra/*.ts` using [SST](https://sst.dev): `sst.cloudflare.Worker` native end to end, with no `wrangler.toml`, no hand-written `wrangler.json`, and no `wrangler deploy` called outside of SST. One single deploy path.

## Database: Postgres via Cloudflare Hyperdrive

Cloudflare Workers can't hold a direct TCP connection to Postgres, so the database is accessed through [Hyperdrive](https://developers.cloudflare.com/hyperdrive/) (`infra/database.ts`), which pools the real connection. The `postgis` extension is already enabled in the initial migration, for future map-related features.

Migrations live in `packages/functions/src/database/migrations/` (Drizzle Kit). See `packages/functions/src/database/MIGRATIONS.md` for the rollback strategy.

## Setup Steps

### 1. Install Bun

```bash
curl -fsSL https://bun.sh/install | bash
```

On Windows without WSL: `npm install -g bun`.

**Prompt for AI agents:**
```text
Check for Bun with `bun --version`. If it's missing, run
`curl -fsSL https://bun.sh/install | bash` (Windows without WSL:
`npm install -g bun`), then confirm the version again before continuing.
```

### 2. Configure Cloudflare access

**Where to create the token**: in the Cloudflare dashboard, **Manage Account → Account API Tokens** (or directly at [dash.cloudflare.com/profile/api-tokens](https://dash.cloudflare.com/profile/api-tokens)) → **"+ Create Token"** → **"Create Custom Token"**.

On the policy screen (the layout changes occasionally — use the **"Search for a permission group..."** box if you can't find something by category):

1. Keep or rename the token name, then click **Edit Cloudflare Workers**:

   ![Token name](/images/docs/token-name-cloudflare.webp)
   ![Edit Cloudflare Workers](/images/docs/Edit-Cloudflare-Workers.webp)

2. On the first policy, click **"All zones ... Account"** to add a second policy scoped to a **zone** (Workers Custom Domains requires this separately from the account-scoped policy):
   - Switch that policy's scope to **"Specified Domains"** and pick your domain:

     ![Specified domains](/images/docs/pecified-domains.webp)

   - Search **`Workers Routes`** and check **Edit** — not `DNS: Edit`. Workers Custom Domains creates the DNS record automatically behind this permission:

     ![Workers Routes](/images/docs/Workers-Routes.webp)

3. On a second policy scoped to **"Entire Account"**, add at minimum (search each term and check **Edit** — it's fine if more comes checked by default):
   - `Workers Scripts`
   - `Workers KV`
   - `Workers R2`
   - `Queues`
   - `Hyperdrive`

   Confirm every permission is set to Edit:

   ![Edit account permissions](/images/docs/edit-account.webp)

4. Click **"Review token"**, then **"Create Token"**:

   ![Review token](/images/docs/Review-token.webp)
   ![Create token](/images/docs/create-token.webp)

5. Save the token somewhere safe. What you'll actually use going forward are the **API token** and the **Account ID**:

   ![Tokens](/images/docs/tokens.png)

Copy the token value now — it's only shown once.

Keep both values handy: they need to be a real **environment variable** ([step 5](#5-set-up-secrets)) *and* go into the `.env` file you load into the secrets vault. They're the only two variables that need both.

**Prompt for AI agents:**
```text
This step has no CLI equivalent — token creation only happens in the
Cloudflare dashboard. Stop and ask the user to follow the steps above,
then get their CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID before
continuing to the next step.
```

### 3. Clone and install

```bash
git clone https://github.com/pedped-app/nuxfire.git
cd nuxfire
bun install
```

Migrations are already versioned in `packages/functions/src/database/migrations/`. You only need to generate new ones if you change `packages/functions/src/database/schema.ts`:

```bash
cd packages/functions
DATABASE_HOST=... DATABASE_PORT=5432 DATABASE_USER=... DATABASE_PASSWORD=... DATABASE_NAME=... \
  bunx drizzle-kit generate
```

(No `DATABASE_URL` — `drizzle.config.ts` reads host/port/user/password/name separately, so you never have to build or escape a URL containing a password.)

**Prompt for AI agents:**
```text
Run: git clone https://github.com/pedped-app/nuxfire.git && cd nuxfire && bun install
Only run `bunx drizzle-kit generate` (from packages/functions) if
schema.ts changed — ask the user for their real DATABASE_HOST/PORT/
USER/PASSWORD/NAME first, never invent placeholder values.
```

### 4. Configure `config.ts`

Fill in your domain and feature flags. Set `prodDomain`/`devDomain` to your real domain, and disable in `flags` any integration you won't use (Stripe, Paddle, websockets, queues, whichever email providers you don't need) — this reduces how many secrets you have to configure.

```typescript [config.ts]
export const prodDomain = "yourdomain.com";
export const devDomain = "dev.yourdomain.com";
export const authEmail = {
  name: "Your Company",
  address: "contact@yourdomain.com",
};
export const authEmailDomain = "yourdomain.com";

export const flags: {
  stripe?: boolean;
  paddle?: boolean;
  googleAuth?: boolean;
  githubAuth?: boolean;
  resend?: boolean;
  mailgun?: boolean;
  ses?: boolean;
  sparkPost?: boolean;
  smtp?: boolean;
  websockets?: boolean;
  cron?: boolean;
  jobsQueue?: boolean;
} = {
  stripe: true,
  paddle: true,
  githubAuth: true,
  googleAuth: true,
  resend: true,
  websockets: true,
  jobsQueue: true,
};
```

**Prompt for AI agents:**
```text
Open config.ts. Ask the user for their real domain and which
integrations they want before editing prodDomain, devDomain, authEmail,
authEmailDomain, and the flags object — do not guess or invent any of
these values.
```

### 5. Set up secrets

NuxFire doesn't use a `.env` file in production — secrets live only in SST's own vault. Today's deploy path is 100% Cloudflare/SST; automated deploy via GitHub Actions (or any other CI) is future work, not an alternate path that exists today.

Not sure where a specific value comes from? [Environment Variables](/docs/saas-starter-kit/getting-started/environment-variables) has a direct link for every provider — Cloudflare, your Postgres host, each email/OAuth/payment provider, and how to generate the two platform-admin secrets yourself.

`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` can't just be stored as an SST secret — SST requires both as a **real environment variable** on every command (`secret load`, `secret set`, `deploy`, `dev`...), because that's the credential that authenticates SST to Cloudflare before it can even read the vault.

**PowerShell** (default on Windows):

```powershell
$env:CLOUDFLARE_API_TOKEN = "your_token"
$env:CLOUDFLARE_ACCOUNT_ID = "your_account_id"
```

To persist across terminals: `[Environment]::SetEnvironmentVariable("CLOUDFLARE_API_TOKEN", "your_token", "User")` (and the same for the account ID) — open a new terminal afterward.

**bash/zsh**:

```bash
export CLOUDFLARE_API_TOKEN=your_token
export CLOUDFLARE_ACCOUNT_ID=your_account_id
```

To persist, add both lines to `.bashrc`/`.zshrc`.

Then load the rest of the secrets into SST's vault — **one file per stage**, never a single reused `.env`. `.env.example` is the template (every key, values blank):

```bash
cp .env.example .env.stage
# fill in .env.stage with your dev environment's values
bunx sst secret load .env.stage --fallback
```

`.env.stage`/`.env.production` are excluded from commits automatically (`.gitignore` covers `.env*`) — keep them locally, don't delete them after loading. You'll need them again whenever a secret changes.

**Prompt for AI agents:**
```text
Ask the user to export CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID in
their own shell first — never request, type, or store these values
yourself. Then: cp .env.example .env.stage, ask the user to fill it in
themselves (never fill in a credential on their behalf), then run
bunx sst secret load .env.stage --fallback.
```

### 6. Deploy your instance

```bash
bun run deploy
```

Deploys to your personal dev stage (SST uses your system username as the stage name by default).

**Prompt for AI agents:**
```text
Run `bun run deploy`. If it fails, check the error against AGENTS.md's
"Infra / SST gotchas" and "Database" sections before proposing a fix —
several documented failures (Supabase pooler/direct mismatch, missing
workers.dev subdomain, unenv version conflicts) read like a different
problem than they actually are.
```

### 7. Development workflow

Local dev server (uses wrangler/miniflare to emulate Cloudflare bindings):

```bash
bun run app    # run the main app locally
bun run web    # run the public site locally
```

Remote dev (connects to infrastructure you've already deployed, instead of emulating it):

```bash
bun run app-remote
bun run web-remote
```

**Prompt for AI agents:**
```text
Ask which the user wants: local (bun run app / bun run web — emulates
Cloudflare bindings) or remote (bun run app-remote / bun run web-remote
— connects to the deployed stage). Run only the one they choose.
```

### 8. Initial data

No manual step here: `packages/functions/src/database/seed.ts` runs on every deploy, right after migrations (see `infra/utils/nuxt.ts`), and creates the Free plan plus the system roles/permissions — idempotent, so running it again never duplicates anything.

Paid plans are deliberately left out of the seed (Stripe/Paddle price IDs are per environment) — they're created at `/admin/plans` by the platform owner.

The platform-owner account and MFA-gated `/admin` console are a separate manual step — see [Platform Admin Console](/docs/saas-starter-kit/features/platform-admin).

**Prompt for AI agents:**
```text
No seed action needed here. If the user needs a platform-owner account,
follow the production bootstrap in the Platform Admin Console doc
(grant-platform-admin.ts against a user who already signed up normally)
— never seed a known owner password against a real environment, and
never wire owner creation into an automated deploy step.
```

## Deployment Stages

- **Development**: uses your system username as the stage name by default.
- **Production**: fill in `.env.production` with real production values, load it, and deploy:
  ```bash
  bunx sst secret load .env.production --stage production
  bun run deploy -- --stage production
  ```
- **Custom stages**: `bun run deploy -- --stage custom-name` (the `--` is required to pass the flag through the `bun run` wrapper).

**Prompt for AI agents:**
```text
For production: confirm .env.production is filled with real production
values (never copy .env.stage's values into it), then run
bunx sst secret load .env.production --stage production (no --fallback)
followed by bun run deploy -- --stage production.
```
