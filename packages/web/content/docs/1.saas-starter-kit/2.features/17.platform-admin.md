`/admin` is a parallel authority system for the SaaS owner/operator — it is **not** built on the per-tenant RBAC that the rest of the app uses ([Role-Based Access Control](/docs/saas-starter-kit/features/rbac)). Nothing here is scoped by team, and every route sits behind its own gate rather than the tenant `Can`/ability system, precisely so a tenant-scoped permission can never grant platform-scoped access.

## The three gates

Every `/admin/*` procedure runs through `platformAdminProcedure`, which requires all three to pass:

1. An **active** (non-revoked) row in the `PlatformAdmin` table for the caller.
2. **MFA enrolled** on that row (`mfaEnabledAt` set).
3. A currently valid **elevated session** — proof a TOTP code was verified in the last 30 minutes. Being logged into the app all day is not enough on its own.

All three failures return the same undifferentiated `FORBIDDEN` — which gate was missed isn't information a caller (or an attacker) needs. There are two platform roles, `SUPER_ADMIN` and `SUPPORT`; the console today doesn't yet differentiate what each can do beyond that shared gate.

## Getting your first platform-admin account

There is no UI to self-register as a platform admin. Common setup, either way:

1. Apply migrations: `bunx drizzle-kit migrate` (from `packages/functions`).
2. Configure the two secrets every `/admin/*` route requires. Without either, the routes fail closed rather than degrading to an insecure mode:
   ```bash
   sst secret set PLATFORM_MFA_SESSION_SECRET "$(openssl rand -base64 32)"
   sst secret set PLATFORM_ADMIN_ENCRYPTION_KEY "$(openssl rand -base64 32)"
   ```
   The first seals the 30-minute elevated-session cookie and can be rotated at any time. The second encrypts every admin's TOTP secret at rest — rotating it invalidates MFA for every admin already enrolled, so treat it as long-lived.
3. Deploy: `bun run deploy`.

From here, the correct path depends on whether this is a real installation or a local/demo one — they are **not interchangeable**.

### Production and staging: promote a real account

Never seed a platform owner with a known password on an environment anyone can reach. The correct pattern (the same one Django's `createsuperuser` or a Rails console grant use — a real account first, authority granted to it after) is two steps, both manual by design:

1. **The real owner signs up through the normal flow** — `/signup` or an OAuth provider, exactly like any tenant user would, choosing their own password. No platform-admin credential is ever written to a script, a doc, or an env var.
2. **Someone with database access promotes that existing account**, from `packages/functions`, against the same `DATABASE_*` values as every other local script:
   ```bash
   bun run src/database/grant-platform-admin.ts --email=owner@yourdomain.com --role=SUPER_ADMIN
   ```
   `grant-platform-admin.ts` only grants (or restores a revoked) `PlatformAdmin` row for a user that already exists — it errors if the email hasn't signed up yet, and it never touches credentials. Like the seed script below, it's deliberately kept out of `infra/utils/nuxt.ts` and every other automated deploy step: running a grant on every deploy is exactly how "one forgotten environment variable" turns into a permanent super-admin nobody remembers creating.
3. The owner logs in with the password they already chose. The app redirects to `/admin` → automatically on to `/admin/mfa` — the account has authority now, but nothing opens until MFA is enrolled.

There's no forced "change your password on first login" step and no dedicated self-registration page for admins, because neither is needed: the password was always the owner's own, chosen before they ever had platform authority. That also closes the one real gap a shared default credential would open — with no known password to race for, there's no scenario where someone other than the intended owner logs in first and claims the MFA enrollment for themselves.

### Local development and demos only: seed both accounts at once

`seed-demo-accounts.ts` creates **both** a platform owner and a demo tenant client in one call, with known default credentials — convenient for trying the product end to end, wrong for anything a stranger could reach:

```bash
AUTH_URL=... AUTH_ADMIN_SECRET=... \
  bun run src/database/seed-demo-accounts.ts \
  --owner-email=owner@yourdomain.com --owner-password=...
```

(`AUTH_URL`/`AUTH_ADMIN_SECRET` come from the shell environment, not the vault — see the script's own header comment for exactly where to read them from a deployed stage.) Passing `--owner-email`/`--owner-password`/`--client-email`/`--client-password` overrides the defaults defined in the script's `parseArgs()` — if you ever run this against an environment anyone outside your team can reach, always pass your own values for both, never the defaults. The defaults exist purely for local/demo convenience, precisely because they're meant to be throwaway; left unset on a reachable environment, a known owner password is a live credential-stuffing target, not a placeholder.

## MFA: enrollment and reauthentication

`/admin/mfa` is the one screen under `/admin` that doesn't assume MFA is already resolved — it's where it gets resolved, via a plain endpoint deliberately outside `platformAdminProcedure`.

- **QR code** is generated entirely in the browser with [`uqr`](https://github.com/unjs/uqr) (zero runtime dependencies) and inlined as an SVG data URI. The shared TOTP secret is in that URI, so it never touches a hosted QR-image service, or any other network request.
- **Enrollment and reauthentication share one flow**: both end in the same six-digit code, posted to `/api/admin/mfa/verify` (first-time enrollment) or `/api/admin/mfa/challenge` (renewing an expired session) — only the copy and the QR step differ.
- The **elevated session** lasts 30 minutes, sealed in an `nuxfire-platform-mfa-verified` cookie (h3's own session sealing — not a hand-rolled token). Once it expires, any `/admin` action prompts for a fresh code, without re-enrolling.
- Wrong codes are rate-limited on three independent fronts: password/code login, enrollment attempts, and reauthentication attempts — each its own limit, none touching the OAuth providers.

**Known limit:** a lost authenticator has no self-service recovery today. Getting an admin back in requires a direct database edit to clear that admin's `mfaEnabledAt`, then re-enrolling.

## What the console does

- **Companies** (`/admin/companies`) — cross-tenant list of every team, with search, plan and status filters; suspend and reactivate any team. Every action is scoped explicitly by team id, never by the caller's own memberships.
- **Plans** (`/admin/plans`) — create, edit, archive/unarchive plans (archiving is a soft delete: `Team.planId` and `Subscription.planId` are real foreign keys, so a plan row is never hard-deleted while teams reference it). Also runs the one-off Stripe cancel-configuration setup.
- **Queue** (`/admin/queue`) — job status counts, dead-letter messages with replay, and the last 20 cron log lines. Job processing is treated as infrastructure of the SaaS itself, not a tenant feature.
- **Audit log** (`/admin/audit-log`) — read-only trail of every platform-admin mutation: `actorUserId · action · target · ip · createdAt`. Writing is centralized in one function (`recordAuditLog`), never a direct insert from a router, so no future admin route can forget to log. The actor is looked up by a best-effort join, not a foreign key — a line survives the actor's own account being deleted later, which is exactly the line an operator most needs to see.

## Other known limits

- No tenant impersonation by the platform owner.
- No IP allowlisting for `/admin` yet.
- No self-service action to move an existing team onto a different plan — only creation and status changes.
